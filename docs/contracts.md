> **Single Source of Truth** for all 13 backend services (`gateway`, `user`, `product`, `cart`, `promotion`, `order`, `payment`, `shipping`, `notification`, `search`, `chat`, `assistant`, `aiops`), the Next.js multi-tenant web BFF (`web/`), and QA/E2E after unifying `main` (+ `3b-3`) and `phase-0b` (see [ADR-0010](adr/0010-unify-main-and-phase-0b.md)).

### Standard Ops Endpoints (Every Service HTTP Port)
Every backend service (`8080..8092`) MUST expose:
- `GET /healthz` → `200 OK` `{"status":"ok","service":"<name>"}`
- `GET /readyz` → `200 OK` when hard DB/Redis/NATS dependencies are reachable, else `503 Service Unavailable` (`search` checks `search-postgres`, Redis, and NATS; it does NOT fail `/readyz` when only Meilisearch is down so gateway/search fallback stays reachable — G13)
- `GET /metrics` → Prometheus text format exposing RED metrics:
  - `http_requests_total{service,method,route,status}`
  - `http_errors_total{service,method,route,status}`
  - `http_request_duration_seconds{service,method,route}`
  - `grpc_requests_total{service,method,code}`
  - `grpc_errors_total{service,method,code}`
  - `grpc_request_duration_seconds{service,method}`

## 3. Global REST API Conventions (Gateway `:8080`)

### Headers
- `Authorization: Bearer <access_token>` — Required on authenticated routes. HS256 JWT (TTL `15m`) with claims: `sub` (user ID), `role` (`buyer`|`seller`|`admin`|`super_admin`|`moderator`|`cskh`|`accountant`|`ops`), `shop_id` (always empty `""` whenever `role != "seller"`, including on login and refresh for demoted users), `jti`, `iat`, `exp`.
  - **Immediate token revocation (`Redis`)**: `user` sets `user:revoked_before:<user_id>` to Unix epoch seconds (TTL = access token TTL + 1m, i.e. 16m) whenever an account is locked, its role changes, its password is reset, or its shop is suspended (role changes, password resets, and shop suspension also revoke all refresh tokens — F12). Gateway fetches `user:revoked_before:<user_id>` together with per-token revocation state in a single `MGET` call and rejects tokens with `iat <= revoked_before` (`401 Unauthorized`). Redis errors fail closed with `503 Service Unavailable`.
- `Idempotency-Key: <unique-key>` — Required on `POST /api/v1/checkout`, `POST /api/v1/payments/{id}/retry` (F5), and money-mutating admin actions (`POST /api/v1/admin/payments/{id}/refund`, `POST /api/v1/admin/refunds/{id}/settle`, `POST /api/v1/admin/reconciliation/queue/{id}/resolve`). Replays return the idempotent result without duplicate side effects (on checkout, replays reuse stored payment/QR/pay_url/warnings metadata while reloading current sub-orders from DB and current `checkout_groups.payment_status` — see §6).
- `traceparent` — Optional W3C TraceContext header; gateway propagates across gRPC/HTTP/NATS and echoes `X-Trace-Id` on every response.
- Webhook security headers:
  - `X-Signature`: lowercase hex HMAC-SHA256 of the raw request body using `PAYMENT_WEBHOOK_SECRET` (or `SHIPPING_WEBHOOK_SECRET`).
  - `X-Timestamp`: Unix epoch seconds (string). Rejected if skew exceeds 5 minutes (300s) for replay protection.

### Money & JSON Representation
- **All monetary amounts are 64-bit integer VND** (`*_vnd`, JSON integer, never floats).
- **Timestamps** are ISO-8601 / RFC3339 UTC strings (`2026-11-20T02:30:00Z`).
- **Standard error envelope**:
```json
{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "SKU sku-123 does not have enough available stock",
    "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
  }
}
```
- **Standard paginated list envelope**:
```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 42
}
```
  - **Pagination overflow guard**: Gateway `httpx.ParsePagination` defaults `(page=1, page_size=20)`, caps `page_size` at `100`, and rejects any `page` value where `page > math.MaxInt32` or `(page - 1) * page_size > math.MaxInt32` (including positive `int64` overflow) with HTTP `400 INVALID_ARGUMENT` across all paginated REST list routes.
- **RBAC Defense-in-Depth & Single Capability Matrix (F9/F10)**: Gateway validates JWT + route capability and forwards **only** `Authorization: Bearer <token>` in gRPC metadata (plain `x-user-id` / `x-user-role` / `x-shop-id` metadata is ignored). Every backend service re-verifies the signed JWT on incoming gRPC calls and enforces both capability RBAC and object-level ownership (e.g., buyer can only read/cancel their own order; seller can only mutate their own `shop_id`'s products/orders; strict staff hierarchy `RoleRank(actor) > RoleRank(target)` prevents peer/upward mutations and protects the last `super_admin` — F10). All admin capabilities are defined in one shared data file [`pkg/common/auth/capabilities.json`](../pkg/common/auth/capabilities.json), embedded in Go (`go:embed`, `auth.HasCapability(claims, cap)` which rejects service tokens) and read directly by Rust `services/payment/src/auth.rs` (`include_str!("../../../pkg/common/auth/capabilities.json")`; copied by `services/payment/Dockerfile` from repo root build context — see §4.11). Internal service-to-service calls without an end user (saga compensation, background jobs, consumers) use short-lived HS256 service tokens signed by `SERVICE_JWT_SECRET`, accepted only on allowlisted RPCs (`internalRPCs` in `pkg/common/auth/auth.go` for Go services; per-RPC `SERVICE_METHOD_ALLOWLIST` in `services/payment/src/auth.rs` for `payment`).

### Multi-Tenant Host Routing, `bff` Network & Sales Channel (`STOREFRONT` vs `MARKETPLACE`)
- **Host Isolation (`web/src/lib/site/host.ts` & `web/src/middleware.ts`, `SITE_ROOT_DOMAIN=nexusmart.localhost`)**:
  - **Root host** (`<SITE_ROOT_DOMAIN>`, `localhost`, `web`, or IP literal): serves platform landing + published-site directory (`(shop)`), Seller Center (`/seller/**`), Admin Portal (`/admin/**`), auth (`/dang-nhap`, `/dang-ky`, `/quen-mat-khau`, `/dat-lai-mat-khau`), and `308` permanent redirects from `/gian-hang/[slug]` & `/san-pham/[slug]` to the shop's published site. Buyer commerce BFF APIs (`/api/{assistant,cart,chat,checkout,orders,payment-methods,payments,products,refunds,returns,search,shipping/addresses,shipping/shipments,shop-discounts,vouchers}/*`) return `404` on the root host.
  - **Storefront site host** (`<subdomain>.<SITE_ROOT_DOMAIN>` or verified custom domain): rewritten internally to `/s/[host]/**` (`(site)`). Direct external `/s` or `/s/*` returns `404` on all hosts; `/seller*`, `/admin*`, and seller/admin APIs return `404` on site hosts. `GET` page requests on a site's default subdomain return `308` to its active custom `primary_host`. Auth cookies (`__Host-nm_at`/`nm_at`, `__Host-nm_rt`/`nm_rt`) are strictly host-only (`HttpOnly`, `SameSite=Lax`, no `Domain=`); BFF derives `shop_id` strictly from `Host` + published site lookup and ignores client-supplied `sales_channel`/`storefront_shop_id`.
- **Internal `bff` Network & Trusted Proxies (`docker-compose.yml` & `services/gateway/internal/middleware/clientip.go`)**:
  - `docker-compose.yml` defines an isolated `bff` network (`internal: true`, subnet `172.31.250.0/28`). `gateway` exposes alias `gateway-bff` on `bff`, and `web` connects via `GATEWAY_URL=http://gateway-bff:8080`.
  - Gateway parses `TRUSTED_PROXIES` (default `172.31.250.0/28`, falling back to `TRUSTED_PROXY_CIDRS`), trusting `X-Forwarded-For` / `X-Real-IP` strictly from peers within those CIDRs so external callers and other containers cannot spoof client IPs.
- **Sales Channel Rules (`services/gateway/internal/router/sales_channel.go`)**:
  - `POST /api/v1/checkout`: omitting `sales_channel` defaults to `"STOREFRONT"` and **requires** non-empty `storefront_shop_id` (else `400 INVALID_ARGUMENT`). Explicit `"MARKETPLACE"` (requiring empty `storefront_shop_id`) remains accepted at gateway/service for the audited multi-shop saga and backend E2E; `web/` BFF always sends `"STOREFRONT"` and never sends `"MARKETPLACE"`.
  - Read/preview/reconciliation endpoints accept optional `sales_channel` (`"STOREFRONT"` | `"MARKETPLACE"`; empty = all channels on filters, `"MARKETPLACE"` on read/preview default) so Admin/Seller retain read-only visibility into historical `MARKETPLACE` orders/ledger. Legacy records with empty `sales_channel` serialize as `"MARKETPLACE"`.

- `SKU` payloads include `min_price_30d_vnd` (computed from `sku_price_history`, defaulting to `price_vnd` when no lower price occurred in the past 30 days) for flash sale minimum-price validation and shop discount price-inflation checks. Storefront `original_price_vnd` (strikethrough price) comes from active shop discount programs / flash sales, never manual input.
- **Commission visibility (D1)**: Gateway strips `commission_rate_bps` completely from all public JSON responses (`/api/v1/categories`, `/api/v1/products`, `/api/v1/products/{id|slug}`, and any public/embedded SKU payloads), while keeping it on `/api/v1/seller/*` (including `GET /api/v1/seller/categories` and own-shop products) and `/api/v1/admin/*` (including `GET /api/v1/admin/categories`). `ProductService` does **not** zero `commission_rate_bps` on active SKUs in `GetSKUsBatch`, because `order` checkout reads `commission_rate_bps` with the buyer JWT.
- **Hidden/inactive SKU redaction in `GetSKUsBatch` (D2)**: `ProductService.GetSKUsBatch` remains public and still returns a row for hidden/inactive SKUs (SKU inactive, product not `APPROVED`/`OUT_OF_STOCK`, or soft-deleted) so `cart` and `order` preserve `SKU_NOT_ACTIVE`/`SKU_INACTIVE` error codes. Callers other than `admin`/`super_admin` or the owning shop `seller` receive only `id`, `product_id`, `shop_id`, `product_name`, `name`, `image_url`, and `is_active = false`; all other fields (`sku_code`, `attributes`, `price_vnd`, `stock`, `reserved_stock`, `available_stock`, `version`, `weight_grams`, `category_id`, `commission_rate_bps`, `min_price_30d_vnd`) are zeroed/empty. Active public SKUs are unchanged.
- **Shop suspension visibility (`products.shop_suspended` — F12)**: When `product` consumes `user.shop_status_changed` with a newer `version`, it toggles `products.shop_suspended` (`true` for `SUSPENDED`, `false` for `ACTIVE`) without altering `products.status`. Public catalog (`GET /products*`) excludes `shop_suspended = true`, `GetSKUsBatch` redacts SKUs of suspended shops with `is_active = false` (D2), and seller mutations (`CreateProduct`/`UpdateProduct`/`UpdateStock`) are rejected with `409 SHOP_SUSPENDED`. Upon unsuspension, `APPROVED` products reappear automatically while seller-`HIDDEN` products remain `HIDDEN`.
- **Banned-keyword normalization, matching & visibility (E9 / E9-bis / E9-ter / E10-bis)** (shared single function in `product`, used by `CreateProduct`, `UpdateProduct`, `AdminReviewProduct`, `CreateReview`, `PreviewBannedKeyword`, `RescanProductsForBannedContent`): NFKC → strip format characters (`unicode.Cf`) and unusual combining marks → fold Cyrillic/Greek homoglyphs → fold leetspeak (`0→o 1→i 3→e 4→a 5→s 7→t @→a $→s`) → collapse ≥3 repeated same-base characters → split into alphanumeric tokens. Matches when: (a) the keyword's token sequence appears contiguously on token boundaries; (b) a single token equals the compact (concatenated) keyword of length ≥ 4; or (c) contiguous short tokens (each length ≤ 2) concatenated contain the compact keyword of length ≥ 4. Never performs full-text compact substring matching across arbitrary words (prevents false positives like `"căn sàn"` matching `"cần sa"`). **E9-bis**: Từ cấm ≥ 2 token, dính liền ≥ 4: token văn bản không dấu so bản bỏ dấu, token có dấu so đúng dấu (`"ma tuy"` khớp `"ma túy"`, `"ma tùy"` không). Từ cấm một token có dấu vẫn so đúng dấu (không cho quy tắc dính liền bỏ dấu vượt qua so đúng dấu, ví dụ `"bổ sung"` không khớp `"súng"`). Quét `name`, `description`, tên SKU, thuộc tính SKU (`attributes`), và `slug` tuỳ chỉnh. Sản phẩm admin đã duyệt (`APPROVED`/`OUT_OF_STOCK`) chỉ về `PENDING` khi có từ `REVIEW` mới (chưa nằm trong `flagged_keywords` đã duyệt); sản phẩm `HIDDEN` không đổi trạng thái vì `REVIEW`. **E9-ter**: Không quét `slug` tự sinh; chỉ quét `slug` khi là slug tuỳ chỉnh mới gửi. So token theo chữ (giữ `â ă ê ô ơ ư đ`) + dấu thanh tách vị trí; dấu kết hợp trên phụ âm và chữ ngoài bảng chữ cái tiếng Việt hạ về chữ gốc; ≥ 3 chữ cùng gốc liền nhau gộp một. Luật ghép chữ rời (c) phải trùng ranh giới token và không mâu thuẫn dấu/hình chữ. `RescanProductsForBannedContent` chỉ khớp `slug` (các trường nội dung khác sạch) → hạ về `PENDING`, không tự `REJECT`. **E10-bis**: `flagged_keywords` và từ khoá khớp chỉ người bán chủ shop và admin thấy; API công khai để trống ngay ở `product`, không chờ gateway lọc. `CheckBannedContent` RPC, seller review replies, and standalone prohibited-category screens are explicitly out of scope in 3b-1 (E12).
- **Shared Product/SKU text, slug & NUL limits (`CreateProduct`, `UpdateProduct`, and CSV import — `services/product/internal/server/server.go`)**: Enforced via `validateProductText`/`validateSKUText`/`validateExplicitSlug` (using `utf8.RuneCountInString` and rejecting NUL `\x00` in every checked field): product `name` ≤ 500 runes, `slug` ≤ 200 characters after normalization (auto-generated slugs from long names are truncated to ≤ 200 characters preferring a dash boundary without error; explicit slugs > 200 characters or lacking alphanumerics fail with `400 INVALID_ARGUMENT` on API and `INVALID_SLUG` during CSV validation), `description` ≤ 20,000 runes, `images` ≤ 20 entries, each product `images[]` URL and SKU `image_url` ≤ 2,048 runes (constant `maxProductImageURLRunes`), `sku_code` ≤ 100 runes, SKU `name` ≤ 255 runes, SKU `attributes` ≤ 30 entries with each key and value ≤ 255 runes. Direct RPCs reject violations with `400 INVALID_ARGUMENT`; CSV import marks offending rows `INVALID` with `INVALID_PRODUCT_TEXT`, `INVALID_SKU_TEXT`, or `INVALID_SLUG` (see §7 for all per-row `error_code` values), rejects NUL bytes in raw CSV with `400 IMPORT_INVALID_UTF8`, and rejects NUL in `filename` while truncating `filename` to 255 runes.

Legacy phase-0b gateway route `GET /api/v1/admin/payments/reconciliation-reports` is NOT mounted (replaced by `/api/v1/admin/reconciliation/runs` and `/queue`). `Payment` and `ShopAllocation` DTOs also include `sales_channel` and `storefront_shop_id`.
- **Allocation, Ledger, Hold Period, Two-Step Refunds & Reconciliation Semantics**:
  - For each sub-order (shop) in a checkout group, let `G = subtotal_vnd`, seller-borne discounts `F = flash_sale_discount_vnd`, `P_shop = shop_program_discount_vnd` (UC-S18), `V_shop = shop_voucher_discount_vnd`, and `S_shop = shop_freeship_discount_vnd` (UC-SHIP06), platform-borne discounts `V_plat = platform_voucher_discount_vnd`, `S_free = freeship_discount_vnd`, `X = coins_discount_vnd`, and full pre-freeship shipping `Ship = shipping_fee_vnd`.
  - **Single item-price rule**: on any single SKU line item, an active flash sale takes precedence over a shop discount program (`F` and `P_shop` never stack on the same line item).
  - **Shop freeship rule**: applies when shop merchandise after `F + P_shop + V_shop` ≥ `free_ship_min_order_vnd`, giving `S_shop = min(Ship, free_ship_max_vnd)`. Platform freeship `S_free` applies afterwards on the remaining shipping fee `Ship - S_shop`. `R` must remain non-negative: if `G - F - P_shop - V_shop - S_shop < 0`, trim `S_shop` so `R >= 0`.
  - Seller net merchandise revenue `R = G - F - P_shop - V_shop - S_shop >= 0`; platform subsidy `D = V_plat + S_free + X`; buyer payable `P = G - F - P_shop - V_shop - V_plat - S_free - S_shop - X + Ship = R + Ship - D >= 0` (`P + D = R + Ship`).
  - **Fees (seller-borne, snapshot at order time)**: category commission `C_cat` (`Order.commission_vnd`) is computed from each line's post-item-discount value using the category's active `commission_bps` (snapshotted on `OrderItem.commission_bps`), capped at `R`. Payment fee `C_pay` (`Order.payment_fee_vnd`) is `P * payment_fee_bps / 10000` using the payment method's active `fee_bps` from `PaymentService.GetFeeConfig` (snapshotted on `Order.payment_fee_bps`), capped so `C_total = C_cat + C_pay <= R`. Both `product` (`category_fee_schedules`) and `payment` (`payment_fee_configs`) select the active schedule where `effective_from <= now` with tie-break order `effective_from DESC, seq DESC`; changing fee schedules with `effective_from` never affects existing orders.
  - `ShopAllocation` carries `subtotal_vnd = R`, `commission_vnd = C_total` (`C_cat + C_pay <= R`), `shipping_fee_vnd = Ship`, `platform_discount_vnd = D`; `Payment.amount_vnd = sum(R + Ship - D) = sum(P)`.
  - Zero-payable orders (`P = 0`) still create a payment (`amount_vnd = 0`, immediately `status = succeeded`, `escrow_status = held`, no QR, no `gateway_clearing` posting) with full `(R, C_total, Ship, D)` allocations so seller settlement credits `R - C_total`.
  - **Escrow Settlement & Seller Hold Period**: On `order.completed`, escrow settlement writes balanced double-entry postings: Debit `escrow_liability` (`P` collected minus refunded), Debit `platform_promo_expense` (`D`, `EXPENSE` account), Credit `seller_pending:<shop>` (`R - C_total` minus refunded merchandise portion), Credit `platform_fee_revenue` (`C_total`), Credit `shipping_fee_payable` (`Ship`), moving the allocation to `pending_release`. `order` does NOT call `ReleaseEscrow`. A background worker in `payment` runs every 60s and transitions `pending_release -> released` (Debit `seller_pending:<shop>` / Credit `seller_available:<shop>`) once `settled_at + PAYMENT_SELLER_HOLD_HOURS` (default `72`) has elapsed, **deferring any allocation that still has an open `pending_approval` refund (`affects_escrow = true`, `is_late_payment = false`) until the checker decides** (F11). `ReleaseEscrow` RPC requires `escrow.release` (`super_admin`, `admin`, `accountant`; removed from service allowlist) and **only accepts `pending_release` allocations** (`held` or `awaiting_collection` returns `409 Conflict`).
  - **COD**: created in `status = pending` with sub-order allocations in `escrow_status = awaiting_collection` (zero ledger postings, no `payment.succeeded` emitted at checkout). On `order.delivered`, `payment` posts Debit `cod_receivable` / Credit `escrow_liability` for that sub-order's `P`, transitions its allocation `awaiting_collection -> held`, emits `payment.succeeded` for that sub-order, and transitions the parent COD payment to `succeeded` once no `awaiting_collection` allocations remain. Cancel before delivery (`order.cancelled`) or failed delivery (`order.returned` with `from_status = SHIPPING`) marks the uncollected allocation `cancelled` with zero ledger postings and transitions the parent COD payment to `cancelled` (or `succeeded` if sibling allocations were already delivered and none remain awaiting collection). Refunds are only permitted for collected payments (VIETQR/ZALOPAY `succeeded` or delivered COD).
  - **Two-Step Refunds & Late Webhooks**: `CreateRefund` records the refund obligation (Debit `escrow_liability` / Credit `refund_payable`, or post-settlement Debit `seller_pending` then `seller_available`, `409` if insufficient) and emits `payment.refunded` (including `idempotency_key`), leaving the refund row in `status = pending` (awaiting bank transfer or ZaloPay wallet refund). End-user callers are barred from the 7 reserved internal prefixes (`order-cancel-refund:`, `order-return-refund:`, `superseded-late-refund:`, `late-webhook:`, `recon-refund:`, `recon-overpay:`, `refund-settle:` → `InvalidArgument`); `refunds.created_by_service` (`payment` migration `0015_p4_refund_lease_and_audit.sql`) restricts the `order-cancel-refund:` amount-check replay exemption strictly to service-created cancel refunds (`order-return-refund:` and all other keys match `amount_vnd` strictly). Total refunded per sub-order includes `pending` refunds and cannot exceed buyer-paid `P`. Buyer submits receiving bank details via `SubmitRefundBankAccount` (`POST /api/v1/refunds/{id}/bank-account`, accepted for `pending` and `manual_review` refunds); admin settles manual bank transfers via `SettleRefund` (`POST /api/v1/admin/refunds/{id}/settle`), posting Debit `refund_payable` / Credit `gateway_clearing`, setting `status = completed` (`REFUND_STATUS_DONE`) + `settled_at`, and emitting `payment.refund_settled`. A late `SUCCEEDED` webhook for a `superseded` payment or cancelled order group auto-creates a `pending` `late_payment` refund without emitting `payment.succeeded`/`payment.refunded`, never mutating order state or overwriting `orders.payment_status`.
  - **Single-Accounting Invariant, Collision Queue & Provider Timestamps**: Every `provider_tx_id` is serialized via a transaction-scoped advisory lock and checked across `payments`, finalized `reconciliation_queue` (`assigned`/`refunded`), and tx-scoped refunds (`late-webhook:*`, `recon-refund:*`, `recon-overpay:*`) so each `provider_tx_id` debits `gateway_clearing` **at most once across all paths** (webhook, expiration scanner, reconciliation run/auto-heal, manual queue resolution). If an incoming webhook/callback carries a `provider_tx_id` already recorded in `webhook_events` for a different provider or different payment/order, `payment` enqueues `reconciliation_queue` with `reason = "provider_tx_id_collision"` (`source_type = "webhook"`, 0 ledger postings) rather than silently discarding it as a duplicate. On every VietQR/ZaloPay confirmation path, `payments.paid_at` records the provider transaction's `occurred_at`/`server_time` timestamp (falling back to `NOW()` only when absent).
  - **Mismatched Transactions (`reconciliation_queue`)**: Admin resolves each queue item via `ResolveReconciliationItem`: `ASSIGN` (exact amount confirms payment like a valid webhook; overpayment confirms and creates a `pending` refund for the excess; underpayment returns `409`), `REFUND` (requires `payment_id`; posts Debit `gateway_clearing` / Credit `refund_payable` and creates a `pending` refund), `SUSPEND` (holds item with note). Every item can only be finalized once, except `SUSPEND` which may be resolved again.
  - **Scheduled/Manual Reconciliation**: Reconciliation dates are evaluated in `Asia/Ho_Chi_Minh`; mock mode reads recorded provider transactions from `webhook_events` (not RAM); SePay uses the real provider transaction timestamp; PayOS without a transaction-list API returns a clear error and marks the run `failed` instead of flagging `missing_provider` in bulk. Any `missing_local` provider transaction not yet accounted for is enqueued idempotently into `reconciliation_queue` (`reason = "reconciliation_missing_local"`) for manual resolution.
  - **ZaloPay v2 E-Wallet (`ZALOPAY`, F1–F4, F8, migrations `0012`–`0016`)**: Only `mock` and `sandbox` modes via `ZALOPAY_MODE` (default `mock`); `ZALOPAY_APP_ID`/`ZALOPAY_KEY1`/`ZALOPAY_KEY2` come strictly from env (empty keys fail `sandbox` startup; never committed or logged — F1). Create (`POST /v2/create`) passes `expire_duration_seconds` from our checkout expiry and stores `app_trans_id` in `provider_order_code` and `order_url` in `payments.pay_url` (web enforces `https://` + allowlisted ZaloPay host; mock uses same-origin mock page — F8). Both the expiry scanner AND `CancelPayment` (for a `pending` `ZALOPAY` payment, bounded by `min(ZALOPAY_HTTP_TIMEOUT_SECS, 5s)`) call `/v2/query` before cancelling (`return_code=1` confirms payment instead of expiring/cancelling; `2|3` or network error cancels normally, persisting `(provider_last_query_return_code, provider_last_query_is_processing)`, late payments follow late-refund flow — F3). **Post-expiry late-payment sweep (`payment` migrations `0014_zalopay_late_payment_sweep.sql` & `0016_zalopay_last_query_state.sql`)**: a multi-replica `FOR UPDATE SKIP LOCKED` sweep scans terminal unpaid `ZALOPAY` payments (`superseded`, `expired`, `cancelled` with `provider_final_status IS NULL`) within `ZALOPAY_LATE_SWEEP_WINDOW_HOURS` (default `24`) in batches of `ZALOPAY_LATE_SWEEP_BATCH_LIMIT` (default `25`) using exponential backoff (`provider_next_check_at`) while persisting `(provider_last_query_return_code, provider_last_query_is_processing)`: `return_code=1` queues a `late_payment` refund (`late_refund_queued`) or `reconciliation_queue` on amount mismatch (`amount_mismatch`); `return_code=2` concludes `provider_final_status = 'not_paid'` and stops sweeping; inside the finite window, `return_code=3` (whether `is_processing=true` or `false`), unknown codes, and transport errors never conclude early and continue retrying with backoff; once the 24h window elapses (`decide_zalopay_window_exhausted`), last observation `(return_code=3, is_processing=false)` or `return_code=2` concludes `provider_final_status = 'not_paid'` without enqueuing `reconciliation_queue`, whereas `is_processing=true`, an unknown `return_code`, or a network error escalates to `reconciliation_queue` (`reason = "zalopay_late_sweep_window_exhausted"`) + `provider_final_status = 'manual_review'`. **Wallet refunds (`payment` migration `0015_p4_refund_lease_and_audit.sql`, F4)**: persist `provider_m_refund_id` before dispatching `/v2/refund`; multi-replica dispatch and `/v2/query_refund` polling use CAS leases (`provider_lease_token`, `provider_lease_until` > worst-case HTTP timeout, `provider_dispatch_attempted`); across GMT+7 midnight rollover, `provider_m_refund_id` rotates to the current VN day either before first dispatch (`provider_dispatch_attempted = false`) or strictly after `/v2/query_refund` returns `return_code=2, sub_return_code=-101` (not found) under CAS (`WHERE provider_lease_token = ... AND provider_refund_id IS NULL`); permanent errors transition to `manual_review` (`provider_status = 'failed'`), unlocking buyer bank-account submission and manual `SettleRefund`; ledger settles `Debit refund_payable / Credit gateway_clearing` only when `return_code=1`.
  - **Two-Person Large Refund Approval (F11)**: Applies to manual admin refunds (`CreateRefund` with end-user JWT) and `AdminResolveReturn(REFUND)` (`CreateRefund` with service token + `require_approval_if_large=true` + `requested_by=admin_id`), NOT automatic saga cancel/late-payment refunds. Triggered when `amount_vnd >= PAYMENT_LARGE_REFUND_APPROVAL_VND` (default `5000000`) OR when the 24-hour rolling sum of manual refunds for the same `payment_id` plus `amount_vnd` reaches the threshold (anti-splitting). `PENDING_APPROVAL` writes zero ledger postings and emits zero `payment.refunded`; only when a different checker (`approved_by <> requested_by` in app + DB CHECK, re-checking `refunds.approve` role at decision time) approves via `DecideRefundApproval` does `payment` lock `FOR UPDATE`, re-check remaining refundable balance, transition to `PENDING`, post the ledger transaction, and write outbox `payment.refunded` in one TX. When rejected (`DecideRefundApproval(approve=false)`), `payment` transitions `PENDING_APPROVAL -> REJECTED` with zero ledger postings and writes `payment.refund_rejected` (`aggregate_id = order_group_id`) to `outbox_events` in the same TX.
  - **COD Carrier File Reconciliation (`ImportCodReconciliation`, E20 / E20-bis)**: Admin uploads UTF-8 CSV (BOM supported, ≤ 2 MiB, ≤ 5,000 rows, columns `tracking_code,cod_amount_vnd,delivered_at[,order_code]`, `cod_amount_vnd` digits-only integer VND; gateway uses dedicated `110s` gRPC timeout and `115s` HTTP read/write deadline). `file_sha256` is stored on `reconciliation_runs` for audit only and is **never** used to skip an entire file (re-uploading the same file after delivery reconciles previously `NOT_DELIVERED` / `MISSING_LOCAL` rows). `payment` executes row processing in a detached Tokio task (`tokio::spawn`) so the run completes and updates `reconciliation_runs.status` cleanly even if the client or gateway disconnects; as a crash safety net, the 60s background worker sweeps any `cod_file` run stuck in `status = 'running'` for > 10 minutes (`600s`) to `status = 'failed'`. Each row runs in its own short transaction serialized by `lock_provider_tx_xact("cod:" + carrier_code + ":" + tracking_code)` so one bad row never blocks others. Lookup matches `payment_shop_allocations.tracking_code` first; optional CSV `order_code` is the NexusMart order reference sent to the carrier (`client_order_code`, equal to `order_id` on initial forward shipments) and is used as a fallback **ONLY** when the allocation has no stored `tracking_code` yet (`a.order_id = order_code OR a.order_code = order_code`): the buyer-facing display `order_code` (from `order.delivered`) can only match after `payment` receives `order.delivered`, so before delivery a row without a matching `order_code` is classified `MISSING_LOCAL` (enqueued in `reconciliation_queue` and auto-closed on re-upload after delivery), whereas a row carrying `order_code = order_id` is classified `NOT_DELIVERED`; **limitation**: re-created forward shipments use `client_order_code = "<order_id>-R<n>"`, which does not match this `order_code` fallback branch (reconciliation relies on `tracking_code` after delivery). Matched rows (exact `cod_amount_vnd`, allocation already `DELIVERED`/`COMPLETED`) post a single balanced ledger transaction `Debit gateway_clearing (P) / Credit cod_receivable (P)` with idempotency key `cod-reconcile:{payment_id}:{order_id}:{shop_id}` (per payment+order+shop, never per file) and auto-close open `cod_file` queue rows for that tracking code **only** when created strictly before the current run (`created_at < run.created_at`), matching the **same `carrier_code`**, and **never** closing `cod_carrier_mismatch` (rows emitted earlier in the same file remain `pending`). Duplicate `tracking_code` rows within the same file or on re-upload yield `ALREADY_RECONCILED` (exact amount, 0 new ledger entries) or `AMOUNT_MISMATCH` (different amount); `AlreadyReconciled` auto-closes **only** pre-run same-carrier `cod_not_delivered` and `cod_missing_local` queue entries and **never** auto-closes `cod_amount_mismatch` or `cod_carrier_mismatch`. Rows that do not reconcile post 0 ledger entries and enqueue into `reconciliation_queue` (`source_type = "cod_file"`, `tracking_code`) with reason: `cod_missing_local` (unknown tracking code), `cod_carrier_mismatch` (matched allocation already stores a non-empty `carrier_code` differing from the uploaded file's `carrier_code`, classified `MISSING_LOCAL`), `cod_not_delivered` / `cod_order_cancelled` (`NOT_DELIVERED`), or `cod_amount_mismatch` (amount mismatch, even 1 VND — keyed by reported amount `cod:<carrier_code>:<tracking_code>:mismatch:<cod_amount_vnd>` while deduplicating any legacy open base-key mismatch row with the same amount, so distinct mismatch amounts for the same tracking code never overwrite each other). The `order.completed` → `seller_pending:<shop>` escrow settlement flow is **unchanged** (never credits sellers twice and never releases seller funds before the 7-day return window; intentional divergence from UC-PAY03 steps 3–4).

### 4.9 Webhooks (Proxied by Gateway & Direct on Target Services)
No JWT required; authenticated via HMAC-SHA256 signature.
- `POST /webhooks/payment` & `POST /webhooks/vietqr` → proxied by gateway (`:8080`) directly to `payment` (`:8086`) preserving raw body, `X-Signature`, `X-Timestamp`, and `traceparent`:
  ```json
  {
    "provider": "vietqr_mock",
    "provider_tx_id": "TXN-20261120-0001",
    "payment_id": "pay-uuid",
    "order_group_id": "grp-uuid",
    "amount_vnd": 250000,
    "status": "SUCCEEDED",
    "reference": "NEXUSMART GRP-UUID",
    "occurred_at": "2026-11-20T02:35:00Z"
  }
  ```
  - Invalid/missing `X-Signature` → `401 Unauthorized` (or `403 Forbidden`).
  - Stale `X-Timestamp` (> 5 min) → `401 Unauthorized`.
  - `status` allowlist (case-insensitive; omitted defaults to `SUCCEEDED` for SePay): `succeeded|success|paid|completed` confirm/reconcile payment; `failed|cancelled|canceled|expired` mark pending payment failed; non-final `pending|processing` return `200 OK` with `{"status":"ignored"}` without persisting `webhook_events`/`provider_tx_id` so a subsequent final webhook with the same `provider_tx_id` is processed normally; any other unexpected status (e.g. `REVERSED`) returns `200 OK` `queued_for_reconciliation:unexpected_webhook_status`, enqueues `reconciliation_queue`, and posts zero ledger entries and zero outbox events.
  - Once a `provider_tx_id` has been recorded in `webhook_events`, any subsequent webhook with the same `provider_tx_id` is treated as a duplicate (`200 OK`, `duplicate: true`, zero duplicate ledger entries, zero duplicate events).
- `POST /webhooks/zalopay` → proxied by gateway (`:8080`) directly to `payment` (`:8086`) preserving exact raw body bytes and `traceparent` (F2, F2-bis):
  ```json
  {
    "data": "{\"app_id\":2553,\"app_trans_id\":\"261124_abc123\",\"zp_trans_id\":261124000001,\"amount\":250000,\"server_time\":1795488000000}",
    "mac": "<lowercase-hex-hmac-sha256-of-raw-data-using-ZALOPAY_KEY2>",
    "type": 1
  }
  ```
  - Response JSON `return_code` is strictly in `{1, -1, 0}` (never `2`, F2-bis):
    - Invalid MAC (`HMAC-SHA256(ZALOPAY_KEY2, raw_data_str) != mac`, constant-time compare) → HTTP `401 Unauthorized` `{"return_code":-1,"return_message":"mac not equal"}` with zero DB writes.
    - Malformed JSON envelope or invalid/mismatched `data.app_id`/`data.app_trans_id` → HTTP `400 Bad Request` `{"return_code":-1,"return_message":...}` with zero DB writes.
    - Confirmed, duplicate/replayed (`data.zp_trans_id` recorded as `UNIQUE` `webhook_events.provider_tx_id`; replaying 10× posts exactly 1 ledger tx), amount-mismatch queued for `reconciliation_queue` (`data.amount != payments.amount_vnd`, without confirming payment), late-refund queued, or terminal ignored → HTTP `200 OK` `{"return_code":1,"return_message":"success"}` (duplicates return `1`, NOT `2` — F2-bis).
    - Transient internal/upstream error or `/v2/query` still processing (`return_code = 3`) → HTTP `200 OK` `{"return_code":0,"return_message":...}` so ZaloPay retries (up to 3×).
  - Replay guard (F2 / F2-bis): `data.server_time` is normalized (`> 1e11` treated as milliseconds, else seconds); if MAC is valid but `|now_sec - server_time_sec| > 300`, `payment` MUST NOT confirm directly from the IPN body — it calls ZaloPay `/v2/query` for `app_trans_id` and processes strictly from the authoritative query result (returning HTTP `200` `return_code = 0` if `/v2/query` is still processing or transiently fails, preserving 300s replay protection without losing delayed ZaloPay callbacks).
- `POST /webhooks/shipping/{carrier}` → proxied by gateway (`:8080`) directly to `shipping` (`:8087`) preserving raw body & `X-Signature`:
  ```json
  {
    "event_id": "ghn-evt-001",
    "tracking_code": "GHN123456789",
    "order_id": "ord-uuid",
    "raw_status": "delivered",
    "description": "Giao hàng thành công",
    "occurred_at": "2026-11-20T09:00:00Z"
  }
  ```
  - Returns `200 OK` immediately after signature verification & idempotent persistence.

## 5. NATS JetStream Event Contracts

### Stream & DLQ Configuration
- **Primary Stream**: `NEXUSMART`
  - Subjects: `user.>`, `order.>`, `payment.>`, `shipment.>`, `product.>`, `promotion.>`, `review.>` (synced in `pkg/common/jetstream/stream.go` and `services/payment/src/workers.rs`; services updating an existing NATS stream MUST union-merge missing subjects via `UpdateStream` rather than overwriting or returning early on `StreamInfo`).
  - Retention: `LimitsPolicy`, Storage: `FileStorage`, Deduplication window: `2m` (`Nats-Msg-Id` set to `event_id`).
- **Dead Letter Queue (DLQ) & Consumer Shutdown Rules (E1, E2 — all 8 consumers: `order`, `shipping`, `notification`, `promotion`, `payment`, `product`, `search`, `assistant`)**:
  - Stream `NEXUSMART_DLQ` capturing `dlq.>` AND local `dead_letter_events` table in every consumer DB (`order`, `shipping`, `notification`, `promotion`, `payment`, `product`, `search`; `assistant` uses `processed_events` + `NEXUSMART_DLQ`).
  - Consumers MUST track processed `event_id` in a `processed_events(event_id PRIMARY KEY, processed_at)` table (`processed_nats_events` in `payment`) inside the same DB transaction as their state update (**idempotent consumer**).
  - After max delivery attempts (default `5`) or on malformed/missing-required-field envelope (including `payment` receiving an order event missing `order_id` — never silently Acked), poison messages are routed to `dead_letter_events` and `dlq.<original_subject>` on `NEXUSMART_DLQ` using a **detached bounded context** (`context.WithoutCancel` + timeout; awaiting `PubAck` on JetStream). A message routed to DLQ MUST only be `Ack`ed **after** persisting to `dead_letter_events` OR publishing to `NEXUSMART_DLQ` (with `PubAck`) succeeds; if both sinks fail, `NakWithDelay` so the message is not dropped. `MaxDeliver` MUST exceed the DLQ attempt threshold (e.g. `MaxDeliver = maxAttempts + 1` or higher) so redelivery remains available if DLQ sinks transiently fail.
  - Errors caused by graceful shutdown (context cancellation / `stopping` flag) MUST NOT be Acked and MUST NOT be routed to DLQ; leave unacked for redelivery instead.
  - Go consumers MUST NOT call `sub.Drain()` or `sub.Unsubscribe()` on durable subscriptions created by the process (`QueueSubscribe(..., nats.Durable(...))`), because `nats.go` deletes the server-side durable consumer upon drain/unsubscribe (disrupting peer replicas and replaying the stream on restart). Instead, set `stopping = true`, wait for in-flight handlers (`wg.Wait()`), and let `nc.Close()` detach cleanly while preserving durables. `promotion` uses `QueueSubscribe` with its existing durable name (upgrading safely without replaying the entire stream). `notification` preserves `sanitizeDLQPayload` (redacting `otp`/`reset_token` including `user.phone_otp_requested` and `user.shop_bank_account_otp`).
- **Trace Propagation**: Publishers inject W3C `traceparent` into NATS message headers AND include `trace_id` inside the JSON envelope.
- **Transactional Outbox Relay (`order`, `payment`, `product`, `shipping`, `user` — D9 / D9-bis / F12)**: Publishers MUST NOT hold a DB transaction open while calling NATS. All 5 services share the same lease-based relay design (shared Go constants, `IsInfraError`, `OutboxRetryBackoff`, and `RunOutboxRelayLoop` in `pkg/common/jetstream/outbox.go`; matching implementation in `payment` Rust):
  - **Strict `seq` ordering & two-tier claim (`locked` + `eligible`)**: Ordering uses monotonic `seq ASC` exclusively in SQL claim queries, `NOT EXISTS` guards, partial indexes, and post-`RETURNING` sort (never `created_at`, because PostgreSQL freezes `NOW()` at `BEGIN TX` before row locks are acquired). Each relay captures a monotonic `leaseDeadline = now + lease` (default `30s`) **before** claiming, claims a batch (`limit = 50`) in a short DB transaction via a 2-stage CTE — `locked` selects claimable rows (`published_at IS NULL` / `status = 'pending'`, `claimed_until IS NULL OR claimed_until <= NOW()`) with `NOT EXISTS` for any earlier unpublished row of the same aggregate holding an active lease/backoff (`claimed_until > NOW()`), `ORDER BY seq ASC LIMIT batch_limit FOR UPDATE OF ... SKIP LOCKED`; `eligible` then excludes any row whose aggregate has an earlier unpublished row not in `locked` — updates `claimed_until = NOW() + lease` and `claim_token`, commits immediately, and publishes outside any DB transaction with `Nats-Msg-Id = event_id` (**at-least-once delivery**; JetStream deduplicates within 2m and consumers deduplicate by `event_id`).
  - **`aggregate_id` & row-lock invariant**: PostgreSQL assigns `BIGSERIAL` `seq` at `INSERT` time, **not** `COMMIT` time; two concurrent transactions inserting for the same aggregate without a shared row lock can commit out of `seq` order and allow a relay to publish a higher `seq` while a lower `seq` is still uncommitted. Therefore every writing transaction MUST hold a row lock on the aggregate entity **before** inserting into `outbox_events`, and `aggregate_id` MUST identify that locked entity:
    - `order`: `orders.id` (from `COALESCE(NULLIF(payload_json->>'order_id', ''), id)`)
    - `shipping`: `shipments.id` (`shipment_id`) for `shipment.updated`, or `shipment_create_jobs.id` (`job_id`) for `shipment.create_failed`
    - `payment`: `order_group_id` (serialized via `lock_payment_group_tx` locking the group's `payments` rows `ORDER BY id ASC FOR UPDATE`)
    - `product`: `products.id` (`product_id`, locked via `GetProductByIDForUpdate` for both `product.reviewed` and `review.created`)
    - `user`: `shops.id` (`shop_id`, locked via `GetShopByIDForUpdate` for `user.shop_status_changed` — F12)
  - **Lease budget guard & `claim_token` finalization**: Before each publish, the relay checks `remaining_lease >= publish_timeout` (default `5s`); on budget exhaustion, context cancellation, lost lease (`0` rows affected on `MarkPublished`), or DB mark error, it bulk-releases deferred + remaining claimed rows in one `UPDATE ... WHERE id = ANY(...) AND claim_token = ...` query and aborts the batch. Crashed workers' leases expire automatically when `claimed_until <= NOW()`.
  - **Non-infra error handling (per-row backoff, no outbox dead-letter)**: On non-infra publish errors (e.g., serialization or invalid subject), the relay increments `attempts`/`retry_count`, records `last_error`, clears `claim_token`, sets `claimed_until = NOW() + min(2^attempts, 60)s` (blocking later events of that aggregate while other aggregates proceed), and bulk-releases later same-aggregate rows in the batch without incrementing their attempts. Outbox rows are **never** marked `failed` or dead-lettered (skipping a failing row would violate per-aggregate order); failing rows remain pending and keep retrying at capped 60s intervals, emitting an `ERROR` alert log (`event_id`, `event_type`, attempt count — no payload) starting at attempt 10 (`attempts >= 10` / `retry_count >= 10`).
  - **Infrastructure error handling & relay loop backoff**: On broker/transport infrastructure errors (`pkg/common/jetstream.IsInfraError` in Go — NATS transport/disconnect/timeout, `ErrInvalidJSAck`, `*nats.APIError` with `Code >= 500`, `net.Error`, context errors — or `ReconnectWithoutCountingRetry` in `payment`), all 4 relays immediately stop the batch, release the errored row's claim with zero per-row backoff (leaving `retry_count` unincremented in `payment`; Go services record `last_error`/`attempts + 1` on the errored row only), and bulk-release all deferred + remaining claims without incrementing their attempts. The relay loop then backs off exponentially (`250ms -> 5s`, sleeping `max(pollInterval, backoff)` while ignoring wake triggers; `payment` also resets its NATS connection) until a poll succeeds.
  - **`seq` backfill & graceful shutdown**: Migrations adding `seq` reassign `seq` for all unpublished/pending rows in strict `(created_at ASC, id ASC)` order using `nextval(pg_get_serial_sequence('outbox_events', 'seq'))` (avoiding physical `ctid` inversions) and require stopping legacy workers prior to migration (`shipping` wraps `ALTER` + backfill inside a column-existence guard because its runner re-executes all `.sql` files). On shutdown, every service waits for its outbox relay and consumer (and background workers) to finish in-flight work before closing NATS connections and DB pools (`payment` bounds worker drain by `WORKER_SHUTDOWN_TIMEOUT`).

### Event Consumer Rules
- `payment` consumes `order.delivered` (per-sub-order COD collection: persists `tracking_code` and `carrier_code` on `payment_shop_allocations` for COD reconciliation (E20), posts Debit `cod_receivable` / Credit `escrow_liability`, transitions allocation `awaiting_collection -> held`, emits sub-order `payment.succeeded`, and marks parent COD payment `succeeded` once no allocations remain awaiting collection), `order.returned` (cancels uncollected COD allocation with zero ledger postings when `from_status = SHIPPING` and `escrow_status = awaiting_collection`; for `from_status = RETURN_REQUESTED`, `order` initiates the idempotent `CreateRefund` call via `order-return-refund:<order_id>`), `order.completed` (settles escrow into `seller_pending` with `pending_release`; 60s hold-release worker moves `pending_release -> released` after `PAYMENT_SELLER_HOLD_HOURS`), and `order.cancelled` (must remain idempotent per `order_id` across repeated deliveries with distinct `event_id`s — e.g., when `order` re-emits `order.cancelled` inside `CompleteCheckoutWithPayment` after a payment is created for an already-cancelled sub-order: allocation cancels guard `escrow_status IN ('awaiting_collection','held')` and auto-refunds deduplicate on deterministic `idempotency_key = "order-cancel-refund:<order_id>"`). Events missing required fields (e.g. `order_id`) are routed to DLQ rather than Acked away (E1).
- `order` consumes `payment.*` (`payment.succeeded`, `payment.failed`, `payment.expired`, `payment.refunded`, `payment.refund_rejected`): events for a non-current/superseded `payment_id` never change order status or overwrite `orders.payment_status`; specifically, when `payment.succeeded` arrives for a non-current `payment_id` on payable sub-orders (`total_payable_vnd > 0`), `order` automatically calls `PaymentService.CreateRefund` (`require_approval_if_large=false`) with deterministic `idempotency_key = "superseded-late-refund:<payment_id>:<order_id>"` (returning errors for consumer retry/DLQ on failure — F5). On `payment.refunded`, `order` accumulates `refunded_vnd` and sets `orders.payment_status = "REFUNDED"` only once `refunded_vnd >= total_payable_vnd`; when `is_post_settlement == false` arrives after `order.completed`, `order` also adds the amount to `settlement_refunded_vnd` so reports match the double-entry ledger (missing `is_post_settlement` on legacy events preserves prior behavior — D10); for a return awaiting large-refund approval (`REFUNDING`), `order` correlates the event via `MatchReturnRefundEvent` (strict `refund_id` match when saved, else fallback to expected `idempotency_key` `order-return-refund:<order_id>` or `order-return-refund:<order_id>:r<attempt>`), marks `refund_approval_status = "APPROVED"` + `refund_done = true`, and completes remaining return side effects. On `payment.refund_rejected` (F11), using the same `refund_id`-then-`idempotency_key` matching against a `REFUNDING` return, `order` transitions the return `REFUNDING -> ESCALATED` (`refund_approval_status = "REJECTED"`, incrementing `refund_attempt`, emitting `order.return_updated` with `reason = "refund_rejected"`) and reverts the order `RETURNED -> RETURN_REQUESTED` so an admin can re-decide; refunds not belonging to a return request are ignored and marked processed. `order` also consumes `shipment.updated` for both `FORWARD` (including `status = "created"` from async retry worker: idempotently attaches `tracking_code`/`label_url`/`carrier_code`/`service_code`, clears `shipment_job_status`, and sets `PREPARING`; if the order is already `CANCELLED` with no `tracking_code` and receives **any** active `FORWARD` event except `"cancelled"` — or a `created` event with a different `tracking_code` — sets `pending_shipment_cancel = true` and runs compensating `ShippingService.CancelShipment`, flagging `orphan_shipment_needs_manual_review = true` if the carrier already picked up — E18; plus shipping/delivery/return lifecycle) and `RETURN` (return request `AWAITING_SHIPMENT -> IN_TRANSIT -> RECEIVED`), and consumes `shipment.create_failed` (sets `orders.shipment_job_status = "FAILED"` when `tracking_code == ""` and appends a generic timeline note omitting internal `error_message` so seller can retry — E18).
- `shipping` consumes `order.cancelled`: cancels any live `FORWARD` shipment and marks any pending/processing `shipment_create_jobs` row `cancelled` (E18).
- `product` consumes `user.shop_status_changed` (durable `QueueSubscribe` + `processed_events` + `dead_letter_events` per E1/F12): rejects payloads with `version <= 0` to DLQ; otherwise idempotently sets `products.shop_suspended = (to_status == "SUSPENDED")` and records `shop_suspension_state.version = version` ONLY when `version > existing version` (so stale older events arriving out of order never overwrite newer state), preserving each product's original `status` (`APPROVED`/`HIDDEN`).
- `promotion` consumes `order.completed` (durable `promotion-order-completed`) and `user.shop_status_changed` (durable `promotion-shop-status`, `QueueSubscribe` + `processed_events` + `dead_letter_events` — F12): rejects `user.shop_status_changed` payloads with `version <= 0` immediately to DLQ; otherwise atomically upserts `shop_suspension_state` (`promotion` migration `007_shop_suspension_state.sql`) ONLY when `version > existing version`. Does NOT consume `order.refunded`.
- `notification` resolves seller owner via `UserService` (`USER_GRPC_ADDR`) and delivers in-app + email notifications to sellers for: new confirmed orders (`order.confirmed`), address changes before pickup (`order.address_updated` — G3, reminding seller to reprint label when `shipment_recreated=true` or `shipment_queued=true`, plus in-app confirmation for buyer, never logging/persisting street address or phone), cancelled orders, new/escalated return requests (`order.return_updated`), returned goods received, failed delivery (`shipment.updated=failed`), returning/returned parcels (`returning|returned`), exhausted shipment creation jobs (`shipment.create_failed`, omitting internal `error_message` from in-app and email content — E18), product moderation decisions (`product.reviewed`), shop suspension/unsuspension (`user.shop_status_changed` — rejects `version <= 0` as malformed to DLQ — F12), and bank-account verification OTP emails (`user.shop_bank_account_otp`, never logging `otp` or placing it in Subject). Buyer order deep links are generated via `services/notification/internal/service/sitelink.go` (resolving published site host through `UserService.GetSiteByShop` + `SITE_URL_SCHEME`/`SITE_URL_PORT`); `/seller` links and `user.registered`, `user.password_reset_requested`, `promotion.voucher_expiring` continue using `WEB_BASE_URL`. Payment labels include `"ví ZaloPay"` alongside `"VietQR"` and `"COD"` (A6). For buyers, `shipment.updated` (`delivering|delivered|failed`) sends email in addition to in-app, `payment.refund_settled` notifies transfer completion, `promotion.voucher_expiring` delivers `PROMOTION` category reminder notifications, `user.phone_otp_requested` delivers SMS-mock verification OTP email to Mailpit (never logging `otp`, never putting `otp` in Subject, redacted in `sanitizeDLQPayload` — E19), and `user.password_reset_requested` emails a link under `WEB_BASE_URL` without logging `reset_token`. Unknown subjects (such as `review.created`, `product.created`, `product.updated`, `product.stock_changed`, `product.upserted`, `product.deleted`, `product.category_updated`) are safely Acked without dirtying DLQ. If `shipment.updated` or `order.return_updated` arrives before `order.created` has populated order participants, the consumer returns an error so NATS redelivers without writing `processed_events` early.
- `search` consumes `product.>` (durable `search-product-events`: `product.upserted`, `product.deleted`, `product.category_updated`) and `user.>` (durable `search-user-events`: `user.shop_reviewed`, `user.shop_status_changed`) following E1 consumer hygiene (`processed_events` + `dead_letter_events` + `NEXUSMART_DLQ`, no `Drain()`/`Unsubscribe()` on durable subscriptions, shutdown cancellation does not DLQ). Replaces the legacy phase-0b durable consumer `search-product-indexer-v1`. `product.upserted` & `product.deleted` gate by `source_updated_at` (rejecting stale out-of-order updates) and write tombstones (`deleted = true`) on delete so concurrent `ReindexAll` never resurrects deleted products (G11). `user.shop_status_changed` rejects `version <= 0` to DLQ and monotonically updates `search_shops.status` (`SUSPENDED`/`ACTIVE`) so suspended shops' products disappear from `SearchProducts`, `HybridSearch`, and `Suggest` within 5 seconds and return upon unsuspension without waiting for per-product events (G10).
- `assistant` consumes `review.created` (durable `assistant-review-summarizer`, idempotent via `processed_events` + `NEXUSMART_DLQ`) to persist public review text and refresh cached product review summaries once `ASSISTANT_MIN_REVIEWS_SUMMARY` (default `10`) reviews accumulate.

## 6. Order State Machine, Return Workflow & Checkout Saga

### Valid Order Status Transitions
- `PENDING` → `CONFIRMED` (payment succeeded), `CANCELLED` (payment failed/expired or buyer cancel)
- `CONFIRMED` → `PREPARING` (seller confirms OR `POST /api/v1/seller/orders/{id}/ship` creates shipment with `tracking_code` — or asynchronously via `shipment.updated` `status="created"` when queued under E18; if carrier returns transient `5xx`/timeout/circuit-open, `order` stores `shipment_job_status="QUEUED"` without advancing status, or `"FAILED"` on `shipment.create_failed`; ship does NOT jump directly to `SHIPPING`), `CANCELLED` (buyer/seller cancel before carrier pickup — if `shipment_job_status == "QUEUED"`, calls `ShippingService.CancelShipment` synchronously first and rejects with `FailedPrecondition`/`409` without cancelling if the carrier already picked up — or auto-cancel job **only while still `CONFIRMED`** past `ORDER_SELLER_CONFIRM_HOURS` default 48h with `cancel_reason = "seller_confirm_timeout"` — checked inside row lock so already-`PREPARING` orders are never auto-cancelled)
- `PREPARING` → `SHIPPING` (on `shipment.updated` `FORWARD` with `delivering|delivered|failed|returning|returned`, emitting `order.shipped`; if `delivered` or `returned` arrives while the order is still `CONFIRMED|PREPARING`, it traverses through `SHIPPING` to the target status within the same transaction with both timeline events and outbox events), `CANCELLED` (before carrier pickup; if `tracking_code` exists or `shipment_job_status == "QUEUED"`, `order` calls `ShippingService.CancelShipment` synchronously first and returns `FailedPrecondition`/`409` without cancelling if the carrier has already picked up the parcel)
- `SHIPPING` → `DELIVERED` (`shipment.updated` `FORWARD` = `delivered`), `RETURNED` (`shipment.updated` `FORWARD` = `returned` after failed delivery)
- `DELIVERED` → `COMPLETED` (buyer confirms received OR auto-complete job after `ORDER_AUTO_COMPLETE_DAYS` default 7d when no return request exists, sharing the exact `BuyerConfirmReceived` completion path), `RETURN_REQUESTED` (buyer creates return request within 7d)
- `RETURN_REQUESTED` → `RETURNED` (when `return_requests.status` enters `REFUNDING`), `COMPLETED` (when `return_requests.status` enters `CLOSED`, via the same completion path as `BuyerConfirmReceived`); `RETURNED` → `RETURN_REQUESTED` (when `payment.refund_rejected` reverts a rejected large return refund and moves the return `REFUNDING -> ESCALATED` — F11)
- Carrier status mapping & monotonic transitions: `picked` maps to `delivering` (carrier has parcel, no longer cancellable); `ready_to_pick|picking` stay `picking` (still cancellable). Shipment status transitions are strictly monotonic (`CanTransitionStatus`): terminal statuses (`delivered`, `returned`, `cancelled`) never transition further, and backward/stale webhooks (e.g., `delivering`/`failed`/`returning` → `created`/`picking`, or `returning` → `delivering`) are ignored without emitting outbox events, while valid redelivery (`failed` → `delivering`) and repeated `failed` are allowed. Cancelled shipments (and `returned` `RETURN` shipments) do not block creating a new shipment for the same order.

### Return Request State Machine (`return_requests.status`)
At most one return request per order (`UNIQUE(order_id)`). Every transition locks the `return_requests` row `FOR UPDATE`, validates current status inside the transaction, appends a `return_events` row, and writes `order.return_updated` to `outbox_events`.

| From | Event / Trigger | To | Next Deadline & Timeout Action |
| --- | --- | --- | --- |
| *(new)* | Buyer `POST /orders/{id}/return` (`DELIVERED`, ≤ 7d) | `PENDING` | `ORDER_RETURN_SELLER_RESPONSE_DAYS` (3d) → auto-accept return (`AWAITING_SHIPMENT`) |
| `PENDING` | Seller `ACCEPT_REFUND` (refund without return) | `REFUNDING` | — |
| `PENDING` | Seller `ACCEPT_RETURN` (or `PENDING` timeout) | `AWAITING_SHIPMENT` (+ create `RETURN` shipment) | `ORDER_RETURN_SHIP_DAYS` (5d) set immediately on entry (refreshed when tracking attaches): expired with tracking → cancel `RETURN` shipment then `CLOSED` (if carrier already picked up, first sync live status via `GetShipment(RETURN)`, else extend `+24h` grace up to max 3 times then `ESCALATED`); expired without tracking → `ESCALATED` |
| `PENDING` | Seller `REJECT` (`note` required) | `REJECTED` | 3d → `CLOSED` |
| `REJECTED` | Buyer `EscalateReturn` | `ESCALATED` | — |
| `AWAITING_SHIPMENT` | `shipment.updated` `RETURN` = `delivering` | `IN_TRANSIT` | 14d → `ESCALATED` |
| `AWAITING_SHIPMENT` | Deadline expires without `return_tracking_code`, OR `shipment.updated` `RETURN` = `returned`/`cancelled` or `failed` (`lost`\|`damage`\|`destroy`) | `ESCALATED` | — |
| `IN_TRANSIT` | Transit deadline (14d) expires, OR `shipment.updated` `RETURN` = `returned`/`cancelled` or `failed` (`lost`\|`damage`\|`destroy`) | `ESCALATED` | — |
| `AWAITING_SHIPMENT` / `IN_TRANSIT` | `shipment.updated` `RETURN` = `delivered` | `RECEIVED` | `ORDER_RETURN_INSPECT_DAYS` (3d) → auto-confirm (`REFUNDING`) |
| `RECEIVED` | Seller `ConfirmReturnReceived` | `REFUNDING` | — |
| `RECEIVED` | Seller `DisputeReturnGoods` (`reason` required) | `ESCALATED` | — |
| `ESCALATED` | Admin `REQUEST_EVIDENCE` | `EVIDENCE_REQUESTED` | 3d → `CLOSED` |
| `EVIDENCE_REQUESTED` | Buyer `AddReturnEvidence` | `ESCALATED` | — |
| `ESCALATED` | Admin `REFUND` | `REFUNDING` | — |
| `ESCALATED` | Admin `RETURN_AND_REFUND` (rejected with `409` if `goods_received = true`, prior `RETURN` shipment is `delivering`\|`returning`\|`failed`\|`delivered`, or escalated from 14d `IN_TRANSIT` timeout) | `AWAITING_SHIPMENT` (+ create `RETURN` shipment) | `ORDER_RETURN_SHIP_DAYS` (5d) set immediately on entry (same expiry rules as above) |
| `ESCALATED` | Admin `REJECT` (cancels live `RETURN` shipment first unless terminal or escalated from 14d transit timeout) | `CLOSED` | — |
| `REFUNDING` | `payment.refund_rejected` (large return refund rejected by checker — F11) | `ESCALATED` | — (order reverts `RETURNED -> RETURN_REQUESTED`) |
| `REFUNDING` | All idempotent post-commit side effects succeed | `REFUNDED` | — |

- **Entering `REFUNDING`**: Within a single DB transaction, transition order `RETURN_REQUESTED -> RETURNED`, write order timeline + `return_events`, and enqueue outbox events `order.returned` (`from_status = RETURN_REQUESTED`) and `order.return_updated`. Post-commit (retried by watchdog until all succeed): (1) `PaymentService.CreateRefund` for remaining `P - refunded_vnd` when `> 0` with idempotency key `order-return-refund:<order_id>` (applies to `VIETQR`, `ZALOPAY`, and collected `COD`; for admin-resolved large refunds, passes `require_approval_if_large=true` and `requested_by=admin_id`, persisted on `return_requests` by `order` migration `0020_return_refund_approval.sql` so watchdog retries preserve maker identity and do not duplicate refunds; while the refund is `PENDING_APPROVAL`, `return_requests.status` stays `REFUNDING`, and on `payment.refund_rejected` `order` transitions the return `REFUNDING -> ESCALATED` and reverts the order `RETURNED -> RETURN_REQUESTED` — F11), (2) `PromotionService.ReleasePromotionShop`, (3) `ProductService.RestockOrderItems` **only** when goods actually reached the seller (`goods_received = true` via `RECEIVED` and not on the disputed-wrong-goods branch). Only after all required side effects succeed does `return_requests.status` transition `REFUNDING -> REFUNDED`.
- **Entering `CLOSED` & `AWAITING_SHIPMENT` Expiry**: Transitions order `RETURN_REQUESTED -> COMPLETED` through the same completion path as `BuyerConfirmReceived` (`order.completed` outbox, reward coins, settlement). When `AWAITING_SHIPMENT` expires with a `return_tracking_code`, the watchdog calls `ShippingService.CancelShipment(RETURN)` **before** moving to `CLOSED`; if the carrier has already picked up the parcel (`FailedPrecondition`), the watchdog first syncs live status via `ShippingService.GetShipment(RETURN)` (service token) and otherwise extends the deadline (`+24h`) **at most 3 times** (`maxReturnDeadlineExtensions = 3`), after which it auto-escalates to `ESCALATED`. When `AWAITING_SHIPMENT` expires with no tracking code (return shipment creation never succeeded), it transitions to `ESCALATED` instead of `CLOSED`. Admin `REJECT` cancels any still-live `RETURN` shipment before closing (except when escalated from the 14d `IN_TRANSIT` timeout, where it closes with an audit note). Admin `RETURN_AND_REFUND` checks `ShippingService.GetShipment(RETURN)` (service token) and rejects (`FailedPrecondition` / `409`) whenever `goods_received = true`, the prior `RETURN` shipment is `delivering`/`returning`/`failed`/`delivered`, or `escalated_from_transit_timeout = true` (admin must choose `REFUND` or `REJECT`).
- **Return shipping fee**: Records `return_fee_vnd` and `return_fee_bearer` (`SELLER` by default when seller accepts; chosen by admin when resolving). Not posted to ledger in Wave 2a.

### Multi-Shop Checkout Saga (`OrderService.CreateCheckout`)
1. **Idempotency check & `FAILED` retry semantics (D11)**: Look up `(buyer_id, idempotency_key)` in `checkout_groups` along with a deterministic SHA-256 `request_hash` of the canonicalized checkout payload (excluding client-supplied `shop_program_item_id`, which is ignored):
   - **`COMPLETED`**: if `request_hash` matches, return HTTP `200` with `idempotent_replay=true` — reusing `payment_id`, QR fields, and `warnings` from the stored snapshot, reloading `orders` from DB for all callers (buyer, seller, admin) with role-based field masking, and setting `payment_status` from `checkout_groups.payment_status` when non-empty. Replaying after sub-orders were cancelled post-completion therefore still returns `200` (`idempotent_replay=true`) with the orders reflecting their current `CANCELLED` status (if `from_cart = true`, server-side `ClearItems` still runs best-effort on replay); if payload differs, reject with gRPC `FailedPrecondition` / HTTP `409 FAILED_PRECONDITION` (`IDEMPOTENCY_KEY_CONFLICT`).
   - **`IN_PROGRESS`** (matching hash): if `needs_cleanup = true` with 0 persisted orders, run `cleanupStaleCheckoutGroup` first (failing with gRPC `Unavailable` / HTTP `503 UNAVAILABLE` if cleanup fails); otherwise wait with progressive exponential backoff (`50ms` doubling up to `1s`, max `15s` total, cancelling immediately on `ctx.Done()`, probing `GetPayment` self-recovery only after `2s`), returning gRPC `Aborted` / HTTP `409 ABORTED` if still in progress past `15s`.
   - **`FAILED` with 0 persisted orders** (pre-persist failure such as out of stock, COD limit, invalid voucher, or `SHOP_PICKUP_ADDRESS_REQUIRED`): reusing the same `Idempotency-Key` is permitted to create a fresh `IN_PROGRESS` checkout group (the partial unique index excludes `FAILED`), **even with a different payload**; if `needs_cleanup = true` is pending, cleanup runs first under the per-key lock (returning gRPC `Unavailable` / HTTP `503 UNAVAILABLE` if cleanup fails).
   - **`FAILED` with ≥ 1 persisted orders** (post-persist failure such as payment failure, all-cancelled/expired group, or concurrent transition to `FAILED` before completion): reusing the same `Idempotency-Key` — or the active checkout observing `finalGroup.Status == "FAILED"` before returning — NEVER returns `200`/`201`, NEVER creates a second order set, and skips cart clearing. It returns gRPC **`FailedPrecondition`** / gateway HTTP **`409 Conflict`** (`error.code = "FAILED_PRECONDITION"`, `error.message = "CHECKOUT_FAILED (<REASON>): checkout attempt failed with reason <REASON>; please retry with a new idempotency_key"`, where `<REASON>` is uppercased `checkout_groups.payment_status`, default `FAILED`, e.g., `EXPIRED`, `PAYMENT_FAILED`). In particular, if **every sub-order is already `CANCELLED` at completion time** (`CompleteCheckoutWithPayment`), the group closes as **`FAILED`** (not `COMPLETED`, without storing a `COMPLETED` response snapshot, and clearing `pending_stock_confirm`), preserving an existing non-`PENDING` reason such as `EXPIRED` (never overwriting with `CANCELLED`). Web BFF normalizes the prefix to code `CHECKOUT_FAILED`, rotates the idempotency key, and directs the buyer to `/don-hang`.
   - **Finalization errors & re-emitting `order.cancelled`**: If `CompleteCheckoutWithPayment` still fails after retries (or fails to build the locked snapshot), `CreateCheckout` returns gRPC **`Unavailable`** / HTTP **`503 UNAVAILABLE`**, does **not** clear the cart, and retrying with the **same `Idempotency-Key`** self-recovers (`tryFinalizeInProgressGroupFromPayment` / `ScanIncompleteCheckoutGroups`). Whenever a payment is created after one or more sub-orders were already `CANCELLED` (empty `orders.payment_id` and `payment_status != REFUNDED`), `order` re-emits `order.cancelled` with a **new `event_id`** inside the **same transaction** as `CompleteCheckoutWithPayment` (both when transitioning `IN_PROGRESS` and when the group is already `FAILED` with a non-empty `payment_id`), so `payment` cancels the allocation/intent or refunds that sub-order's portion; `order.cancelled` consumers MUST tolerate duplicate events per `order_id`.
2. **Validate & Resolve**: Validate buyer (`UserService.ValidateUser`), fetch address (`UserService.GetAddress`; both `province_code` and `ward_code` are mandatory at checkout, else `FailedPrecondition` / HTTP `409 FAILED_PRECONDITION` with `ADDRESS_WARD_REQUIRED` at the start of `error.message` — E17), load items from `CartService.GetCart` (when `from_cart=true`; if any `selected` item has `unavailable=true`, reject immediately with `FailedPrecondition` / HTTP `409` exact `error.code = "SKU_INACTIVE"` before reserving stock/promotions — E4; if 0 items remain, return existing empty-cart error) or `items[]`, fetch SKU details, effective category `commission_rate_bps`, and prices (`ProductService.GetSKUsBatch`), group items by `shop_id`, load shop shipping settings (`ShippingService.GetShopShippingSettings` for `default_weight_grams` fallback and `free_ship_*` rules), resolve each shop via `UserService.GetShop` + `UserService.GetAddress` (**requiring `shop.status == SHOP_STATUS_ACTIVE` at checkout**, rejecting `SHOP_STATUS_SUSPENDED` with `409 SHOP_SUSPENDED` — F12; **never falling back to the buyer's shipping address**; if `UserService` is nil, shop/address is `NotFound`, `pickup_address_id`/`owner_user_id` is empty, or `province_code` is empty, fails with gRPC **`FailedPrecondition`** / gateway HTTP **`409 Conflict`** `error.code = "FAILED_PRECONDITION"`, `error.message = "SHOP_PICKUP_ADDRESS_REQUIRED: ..."`, marking the pre-persist group `FAILED` with reason `SHOP_PICKUP_ADDRESS_REQUIRED`; non-`NotFound` transient lookup errors propagate as-is; the same `resolveShopPickupAddress` guard runs on `SellerShipOrder` — allowing `SUSPENDED` shops to ship already-placed orders per F12 — before marking `pending_shipment_cancel` and on post-commit `ensureReturnShipment`), calculate shipping per shop (`ShippingService.CalculateFee`; COD surcharge at quote time is estimated from the pre-discount subtotal, and quotes report `cod_supported`), read `PaymentService.GetPaymentMethodConfigs` directly (no cache; fail closed with `503 UNAVAILABLE` if unreadable, reject disabled method with `409 PAYMENT_METHOD_DISABLED`, and enforce `min_order_vnd`/`max_order_vnd` — F6/F7), and fetch active payment fee bps (`PaymentService.GetFeeConfig`, service token).
3. **Flash Sale & COD Risk Check (before any stock/promotion reservation — E19 / F6)**: If any line item uses a flash sale, require the flash sale window to be currently active (reject upcoming), disallow `COD` (`FailedPrecondition` / HTTP `409 FAILED_PRECONDITION`, `FLASH_SALE_COD_NOT_ALLOWED`), and use `ORDER_FLASH_PAYMENT_EXPIRY_MINUTES` (default `5`, capped by the earliest flash window `ends_at`). If `payment_method == COD` (shared helper on checkout and `RetryPayment` switch to COD — F5), enforce: (a) `phone_verified == true` when `ORDER_COD_REQUIRE_PHONE_VERIFIED=true` (else `FailedPrecondition` / HTTP `409` exact `error.code = "COD_PHONE_NOT_VERIFIED"`); (b) destination ward/carrier `cod_supported == true` (else `FailedPrecondition` / HTTP `409` exact `error.code = "COD_AREA_NOT_SUPPORTED"`); (c) `cod_rejected_count < ORDER_COD_MAX_REJECTED_COUNT` (3) AND terminal COD order rejection rate check (single indexed query counting terminal COD orders for `buyer_id`: when `total >= ORDER_COD_MIN_ORDERS_FOR_RATE` (3) and `rejected * 10000 >= total * ORDER_COD_MAX_REJECT_RATE_BPS` (3000), reject with `FailedPrecondition` / HTTP `409` exact `error.code = "COD_REJECTED_LIMIT_EXCEEDED"`); (d) `total_payable_vnd <= payment_method_configs[COD].max_order_vnd` (when `> 0`, seeded `5000000`; else `FailedPrecondition` / HTTP `409 FAILED_PRECONDITION` with `COD_LIMIT_EXCEEDED` at the start of `error.message`; checked here before reservation when no promotions/shop freeship apply, and enforced after step 5 with stock/promotion compensation when discounts apply). Also enforce `min_order_vnd`/`max_order_vnd` from `payment_method_configs` for online methods (`409 ORDER_AMOUNT_OUT_OF_RANGE`). Transient `user`/`shipping`/`payment` errors fail closed (`Unavailable` / `503`), never bypassing COD/method checks.
4. **Reserve Stock**: Call `ProductService.ReserveStock(order_id=checkout_group_id, all_items)` (atomic optimistic locking, idempotent).
5. **Reserve Promotions**: Call `PromotionService.ReservePromotion(order_id=checkout_group_id, user_id=buyer_id, ...)` using **`order`'s internal service token** (`claims.Service == "order-service"`, without forwarding the buyer JWT; end-user JWTs and other services are rejected with `PermissionDenied` — D3) — atomic Redis Lua + Postgres checks for flash sale slots with `FlashSaleReservationItem.shop_id`, shop discount program per-user limits with `ShopDiscountProgramReservationItem`, voucher quotas, and coins; single item-price rule: flash wins over shop discount program; order of discount application: `item price (flash OR shop program) -> shop voucher -> shop freeship -> platform voucher -> platform freeship -> coins`. Each `ShopDiscountBreakdown.applied_shop_program_item_ids` reports the `shop_discount_program_item_id`s actually applied and reserved for that shop (lines exceeding `per_user_limit` are excluded, priced at regular price, and not reserved). Redis counters act only as a fast gate while Postgres is the final authority in `CommitReservation` (per-user Redis keys carry a 120s TTL with effective usage = `max(Redis, Postgres)`, a 5s background loop resyncs voucher/flash-sale counters after two consecutive identical drift ticks, and racing boundary checkouts may be rejected at commit time — D12).
   - *On failure*: compensate step 4 via `ProductService.ReleaseStock(checkout_group_id)` and return error.
6. **Persist Checkout Group + Sub-Orders + Outbox** in one PostgreSQL transaction (running under a detached timeout context, locking `checkout_groups FOR UPDATE` and requiring `status = 'IN_PROGRESS'`):
   - One sub-order per `shop_id` sharing `checkout_group_id`, persisting `shop_program_discount_vnd`, `shop_freeship_discount_vnd`, `payment_fee_vnd`, `payment_fee_bps`, `checkout_groups.warnings_json`, and per-item `commission_bps` + `shop_program_item_id` (populated only for items present in `ShopDiscountBreakdown.applied_shop_program_item_ids`).
   - Online (`VIETQR` or `ZALOPAY`, `P > 0`): `status = PENDING`, `payment_status = PENDING`, `payment_expires_at = now + ORDER_FLASH_PAYMENT_EXPIRY_MINUTES` (default `5m`) if any flash sale item is present else `now + payment_method_configs[method].expiry_minutes` (seeded `15m` — F6); COD (`P > 0`): `status = CONFIRMED`, `payment_status = PENDING` (awaiting collection until `order.delivered`); zero-payable (`P = 0`): `status = CONFIRMED`, `payment_status = SUCCEEDED`.
   - **Shipping initialization guard**: while `checkout_groups.status == 'IN_PROGRESS'`, `SellerConfirmOrder` (`CONFIRMED -> PREPARING`) remains allowed, but `SellerShipOrder` and any transition moving an order to `SHIPPING` or beyond (`HandleShipmentUpdated` `FORWARD`, `BuyerConfirmReceived`, `RequestReturn`) are rejected with `FailedPrecondition` (`PAYMENT_NOT_INITIALIZED: đơn đang khởi tạo thanh toán, vui lòng thử lại sau ít phút`) before creating any shipment.
7. **Create Payment**: Call `PaymentService.CreatePayment(...)` under a detached caller context (preserving the buyer JWT while surviving client disconnect; including 0 VND orders where `amount_vnd = 0`) with `shop_allocations` (per-sub-order `order_id`, `shop_id`, `subtotal_vnd = R`, `commission_vnd = C_cat + C_pay <= R`, `shipping_fee_vnd = Ship`, `platform_discount_vnd = D`; `amount_vnd = sum(R + Ship - D)`).
   - *On ambiguous error*: probe `PaymentService.GetPayment(order_group_id)` under a detached service context. If found, reconcile any non-`PENDING` payment status (returning `Unavailable` without completing the group if reconciliation fails) and finalize forward. If `NotFound`: `CONFIRMED` (COD / 0 VND) orders return `Unavailable` without cancelling so the watchdog forward-recovers; `PENDING` (VietQR) orders cancel and compensate. On definite error, cancel sub-orders (`CancelCheckoutGroupOrders`, refusing non-`IN_PROGRESS` groups) and compensate (`CancelPayment`, `ReleasePromotion`, `ReleaseStock` / `RestockOrderItems`).
8. **Clear Cart (`from_cart` semantics)**: Only when `from_cart = true` does `order` clear the ordered SKUs from cart server-side via best-effort `CartService.ClearItems(buyer_id, ordered_sku_ids)` (`RetryIdempotent(3)` under a detached caller context) — **including on `200` idempotent replays**, and never on `FAILED` or `503 UNAVAILABLE`. When `from_cart = false` (Buy Now, or partial-cart checkout from web), the server never touches the cart; for partial-cart checkout (`!isBuyNow && !fromCart`), the web client explicitly clears only the ordered SKUs via `DELETE /api/v1/cart` (`resolvePostCheckoutCartAction`).
9. **Async Payment Failure / Expiry Compensation, Restock, Partial Release, COD Rejection & Watchdogs**:
   - On `payment.failed` or `payment.expired` (matching the checkout group's current `payment_id`): transition sub-orders `PENDING -> CANCELLED`, call `ProductService.ReleaseStock(checkout_group_id)` and `PromotionService.ReleasePromotion(checkout_group_id)`, write `order.cancelled` outbox event. Events for non-current/superseded `payment_id`s are ignored.
   - On `payment.succeeded` (matching the checkout group's current `payment_id`): transition sub-orders `PENDING -> CONFIRMED`, call `ProductService.ConfirmStock(checkout_group_id)`, write `order.confirmed` outbox event. When `payment.succeeded` arrives for a non-current (superseded) `payment_id` on payable sub-orders, do not mutate order state; instead trigger automatic refund `superseded-late-refund:<payment_id>:<order_id>` (`require_approval_if_large=false`).
   - On `payment.refunded` (matching the sub-order's current `payment_id`): accumulate `refunded_vnd` and set `orders.payment_status = REFUNDED` only once `refunded_vnd >= total_payable_vnd`.
   - On `OrderService.RetryPayment` (UC-B25 / F5): supports `VIETQR`, `ZALOPAY`, and switching to `COD`; verifies `payment_id` matches the group's current active payment, every sub-order is `PENDING` and unexpired under advisory lock (races with concurrent retry or expiry yield exactly one outcome), and every shop in the group is `ACTIVE` via `UserService.GetShop` (F12); reads `PaymentService.GetPaymentMethodConfigs` directly (rejects disabled/unconfigured/invalid method or out-of-range amount, exempting `0 VND` orders from `min_order_vnd`); preserves original `checkout_group.payment_expires_at` on online retries/switches; when switching to `COD`, drops `payment_expires_at` (`nil`), rejects flash sale items, and runs the full E19 COD eligibility check (failing closed with `COD_AREA_CHECK_UNAVAILABLE` if `shipping` is unreachable); recalculates `payment_fee_bps`/`payment_fee_vnd` for the new method while keeping `total_payable_vnd` unchanged; creates a superseding payment, atomically updates `orders.payment_id`, `payment_method`, `payment_fee_*`, `payment_expires_at`, and `status` (`CONFIRMED` + `ConfirmStock` on COD switch), and returns `switched_to_cod`, `pay_url`, and `orders`. Late webhooks for the superseded payment create a `late_payment` refund without confirming the order.
   - On cancellation of an order that already has a `tracking_code` or `shipment_job_status == "QUEUED"`: `order` calls `ShippingService.CancelShipment` synchronously first; if the carrier already picked up the parcel (`FailedPrecondition` / `409`), the order remains unchanged (not cancelled). Shipping's `order.cancelled` consumer stays as a safety net.
   - On cancellation of a single sub-order (while active siblings remain): call `ProductService.RestockOrderItems(order_id=sub_order_id, items)` (service-token or admin only, not exposed over REST; atomic stock increment, idempotent per `(order_id, sku_id)` via `stock_history`) and `PromotionService.ReleasePromotionShop(order_id=checkout_group_id, shop_id, reason)` (returns sub-order coins, shop voucher quota, flash sale slots; platform/freeship vouchers are released once all sub-orders in the group are released). When no active sibling remains, full group promotion release (`ReleasePromotion`) and stock release/restock run.
   - On `shipment.updated` (`FORWARD`, `returned`): transition `SHIPPING` (or `CONFIRMED|PREPARING -> SHIPPING -> RETURNED`) `-> RETURNED`, emit `order.returned` (`from_status = SHIPPING`) via transactional outbox, call `ProductService.RestockOrderItems(sub_order_id, items)` and `PromotionService.ReleasePromotionShop(checkout_group_id, shop_id, "order_returned")`; if COD delivery failed, call `UserService.RecordCODRejection(user_id, order_id, reason)`; if paid online (`VIETQR`, `SUCCEEDED`, `total_payable_vnd > 0`), call idempotent `PaymentService.CreateRefund`. On `shipment.updated` (`RETURN`), advance `return_requests` (`AWAITING_SHIPMENT -> IN_TRANSIT` on `delivering`, `AWAITING_SHIPMENT|IN_TRANSIT -> RECEIVED` on `delivered`).
   - On `BuyerConfirmReceived` (`DELIVERED -> COMPLETED`), auto-complete after `ORDER_AUTO_COMPLETE_DAYS`, or return `CLOSED`: write `order.completed` (carrying `coins_reward` computed on buyer actual merchandise payment `min(P, max(0, (G - F - P_shop - V_shop) - V_plat - X))`, excluding shipping and without deducting shop freeship `S_shop`; 0 VND order earns 0 coins) to the transactional outbox; `order` does **not** call `PaymentService.ReleaseEscrow`. `promotion` credits reward coins idempotently on `order.completed`, and `payment` settles into `seller_pending` (`pending_release`) and releases to `seller_available` via its 60s background hold worker after `PAYMENT_SELLER_HOLD_HOURS`.
   - **Watchdogs, Durable Recovery Flags & Scheduled Sweeps**:
     - **Stale `IN_PROGRESS` & Incomplete Checkout Groups, VietQR Expiry**:
       - `ScanStaleCheckoutGroups`: sweeps `IN_PROGRESS` groups with no persisted sub-orders older than `ORDER_STALE_CHECKOUT_AFTER` (default `5m`) as well as groups with `needs_cleanup = TRUE` (`IN_PROGRESS` or `FAILED`, no sub-orders). Uses claim-first two-statement `READ COMMITTED` serialization (`SELECT checkout_groups FOR UPDATE`, then fresh-snapshot `NOT EXISTS (orders)` check, flipping `status = 'FAILED', needs_cleanup = TRUE` before calling `ReleasePromotion` and `ReleaseStock`, and clearing `needs_cleanup = FALSE` only after both succeed).
       - `ScanIncompleteCheckoutGroups`: recovers `IN_PROGRESS` groups that already have persisted sub-orders past `ORDER_STALE_CHECKOUT_AFTER`: probes `PaymentService.GetPayment(order_group_id)` first; if `NotFound`, forward-recovers live (non-`CANCELLED`) `CONFIRMED`/`PREPARING`/`SHIPPING` orders via service-token `PaymentService.CreatePayment` (`idempotency_key = "checkout:" + order_group_id`, `supersede_previous = false`, excluding `CANCELLED` orders from allocations and group total), refuses legacy `DELIVERED`/`COMPLETED`/`RETURN_REQUESTED`/`RETURNED` orders (logs Error for manual reconciliation without closing the group), closes all-`CANCELLED` groups `FAILED`, and cancels/compensates purely unpaid `PENDING` VietQR groups.
       - `ScanExpiredPendingOrders`: sweeps expired `PENDING` VietQR orders after probing `PaymentService.GetPayment` so late `SUCCEEDED`/`REFUNDED` payments are never downgraded to `EXPIRED`.
     - **Pending Stock Confirmation (`checkout_groups.pending_stock_confirm`)**: set atomically when orders confirm (`COD`, 0-VND, or VietQR `payment.succeeded`) and cleared only after `ProductService.ConfirmStock` succeeds (or all sub-orders are cancelled); retried by `ScanPendingStockConfirms`.
     - **Pending Cancel Compensation (`orders.pending_cancel_compensation`)**: set on order cancellation and cleared only after all post-commit compensations (`ReleaseStock`/`RestockOrderItems`, `ReleasePromotion`/`ReleasePromotionShop`, `CreateRefund`, `CancelPayment`) succeed; retried by `ScanPendingCancelCompensations`.
     - **Orphan Shipment Cancel & Manual Review (`orders.pending_shipment_cancel`, `orders.orphan_shipment_needs_manual_review`)**: retries `CancelShipment(FORWARD)` on `CANCELLED` orders with an orphaned shipment (`ScanPendingOrphanShipmentCancels`), including `CANCELLED` orders with empty `tracking_code` that receive any active `FORWARD` `shipment.updated` event (except `"cancelled"`); if the carrier already picked up (`FailedPrecondition`), records an audit timeline note (`MANUAL_REVIEW_REQUIRED`) and flags `orphan_shipment_needs_manual_review = true` for manual admin handling.
     - **Seller Confirm Timeout**: auto-cancels orders **only while still `CONFIRMED`** past `ORDER_SELLER_CONFIRM_HOURS` (default `48`) via the standard cancel path with `cancel_reason = "seller_confirm_timeout"`.
     - **Auto-Complete Delivered Orders**: transitions `DELIVERED` orders past `ORDER_AUTO_COMPLETE_DAYS` (default `7`) with no return request to `COMPLETED` via the shared completion path.
     - **Return Deadline & `REFUNDING` Watchdog**: scans expired `return_requests` deadlines (`PENDING`, `AWAITING_SHIPMENT`, `IN_TRANSIT`, `REJECTED`, `RECEIVED`, `EVIDENCE_REQUESTED`) via randomized batch `SELECT` (`ORDER BY random()` to prevent starvation behind failing rows; `FOR UPDATE SKIP LOCKED` is used only by the outbox relay) and executes each transition under a per-row `FOR UPDATE` lock (`orders` + `return_requests`) that re-validates status and deadline inside the transaction; retries idempotent `CreateReturnShipment` for `AWAITING_SHIPMENT` without tracking, and retries incomplete `REFUNDING` post-commit side effects until `REFUNDED`.
