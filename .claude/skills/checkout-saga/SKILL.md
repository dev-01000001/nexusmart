# NexusMart Checkout Saga & Order Lifecycle

Nguồn sự thật: code trong `services/order/` (`internal/service/`, `internal/statemachine/`, `internal/events/`, `internal/clients/`, `internal/store/`, `migrations/`) và `services/product/` (`internal/server/server.go`, `internal/store/pg_store.go`, `queries/product.sql`, `migrations/`). Khi `docs/contracts.md` §6 lệch với code, **code là nguồn sự thật** (xem mục 7).

## 1. Bảng dữ liệu chính (`services/order/migrations/`)

- `checkout_groups`: lưu phiên checkout theo `(buyer_id, idempotency_key)` với partial unique index `idx_checkout_groups_buyer_idem_active` (`WHERE status <> 'FAILED'`), trạng thái `IN_PROGRESS` | `COMPLETED` | `FAILED`, lưu `request_hash` (SHA-256 kiểm xung đột payload), `response_snapshot_json` để replay, `warnings_json` (migration `0012`) và các cờ bền vững `pending_stock_confirm`, `needs_cleanup` (partial index `idx_checkout_groups_needs_cleanup`, migration `0013`).
- `orders`: 1 đơn con/shop chung `checkout_group_id`, có index `idx_orders_pending_expiry` (`WHERE status = 'PENDING' AND payment_method = 'VIETQR'`). Tiền lưu `BIGINT` nguyên VND (`*_vnd`), gồm `shop_program_discount_vnd`, `shop_freeship_discount_vnd`, `payment_fee_vnd`, `payment_fee_bps`, cùng các cờ phục hồi bền vững `pending_cancel_compensation`, `pending_return_compensation`, `pending_shipment_cancel`, `orphan_shipment_needs_manual_review`.
- `order_items` (kèm `category_id`, `commission_rate_bps`, `shop_program_item_id`), `order_timeline_events`, `return_requests`, `return_events`, `outbox_events` (index `WHERE published_at IS NULL`), `processed_events(event_id PK)`, `dead_letter_events`.

## 2. Trình tự Saga `CreateCheckout` (`services/order/internal/service/checkout.go`)

Mỗi bước dưới đây bám đúng thứ tự thực thi trong `OrderService.CreateCheckout`:

1. **Validate & Idempotency**:
   - Kiểm tra `idempotency_key`, auth (`service.go:requireAuthenticatedCaller`), `address_id`, `payment_method` (`COD`|`VIETQR`), `coins_to_use >= 0`, và tính `request_hash` (SHA-256 canonical payload; dùng lại key với payload khác trả `FailedPrecondition` / `409 IDEMPOTENCY_KEY_CONFLICT`).
   - Fast path `checkout.go:tryLoadIdempotentReplay`: nếu `checkout_groups.status == "COMPLETED"` và khớp `request_hash`, trả `checkout.go:buildReplayResponse` (`idempotent_replay=true`, ưu tiên unmarshal `response_snapshot_json`).
   - Khóa nội bộ theo `buyerID + ":" + idemKey` (`service.go:keyedLocker.Lock`), rồi `checkout.go:acquireCheckoutGroup`: chèn `checkout_groups(status='IN_PROGRESS')`; nếu pod khác đang chạy cùng key thì poll mỗi `50ms` tối đa `15s`, hết hạn trả `Aborted`.
   - Nếu lỗi trước khi lưu đơn con: closure `failGroupBeforePersist` gọi `store.FailCheckoutGroup` (dưới `detachedCompensationContext`) đánh dấu `FAILED` để key thử lại được.
2. **Step A — Xác thực người mua & địa chỉ**: `User.ValidateUser` (yêu cầu `USER_STATUS_ACTIVE`) → `User.GetAddress` (kiểm chủ sở hữu địa chỉ).
3. **Step B — Gom item, kiểm tra Flash Sale & Chương trình giảm giá Shop**:
   - `checkout.go:resolveCheckoutInputs`: đọc `Cart.GetCart` nếu `from_cart=true` (lọc theo `selected` nếu có item được chọn, giữ `flash_sale_item_id` override từ request) hoặc dùng `req.Items`; gộp trùng `sku_id` và sort theo `sku_id`.
   - `Product.GetSKUsBatch` → `checkout.go:buildShopPlans`: kiểm `shop_id`, `is_active`, `price_vnd > 0`, `commission_rate_bps` trong `0..10000` (sai → `INVALID_COMMISSION_RATE`), `available_stock >= qty`, gom thành 1 `shopCheckoutPlan` cho mỗi `shop_id`, sort `plans` theo `shopID` và `stockItems` theo `SkuId`.
   - **Flash Sale** (`checkout.go:217-230`, `resolveActiveFlashSales`): nếu có item Flash Sale, chặn `COD` bằng `codes.FailedPrecondition` (`FLASH_SALE_COD_NOT_ALLOWED`, gateway trả HTTP `409 FAILED_PRECONDITION`), tra `Promotion.ListActiveFlashSales(IncludeUpcoming=false)` qua `stripServiceAuth` và chỉ chấp nhận suất đang diễn ra (`starts_at <= now < ends_at`, `APPROVED`); lưu `earliestFlashEndsAt`.
   - **Chương trình giảm giá của shop (UC-S18)** (`checkout.go:232-238`, `resolveActiveShopDiscounts`): tra phía server qua `Promotion.ListActiveShopDiscounts` (`stripServiceAuth`, bắt buộc `sku_ids <= 200` hoặc `shop_id`) chỉ cho các SKU **không** có Flash Sale (Flash Sale luôn thắng, không chồng `F` và `P_shop` trên cùng SKU).
4. **Step C — Cài đặt vận chuyển shop, tính phí ship & tra phí thanh toán**:
   - `checkout.go:calculateShippingFees`: gọi `Shipping.GetShopShippingSettings` bằng `clients.WithInternalAdminContext` để lấy `default_weight_grams` (dùng khi SKU có `weight_grams <= 0`) và cấu hình shop freeship (`free_ship_enabled`, `free_ship_min_order_vnd`, `free_ship_max_vnd`); tra địa chỉ lấy hàng (`User.GetShop` + `User.GetAddress`) → `Shipping.CalculateFee` → chọn báo giá (`checkout.go:pickShippingQuote`).
   - `checkout.go:lookupPaymentFeeBPS`: gọi `Payment.GetFeeConfig` (service token) theo phương thức thanh toán và thời điểm checkout; lỗi hoặc thiếu cấu hình hiệu lực (`PAYMENT_FEE_CONFIG_NOT_FOUND`) thì fail checkout ngay trước khi giữ kho, không đoán.
5. **Step D — Kiểm tra rủi ro COD sớm** (`checkout.go:254-295`): nếu `COD`, kiểm `cod_rejected_count >= ORDER_COD_MAX_REJECTED_COUNT` (`3`). Chỉ kiểm `preTotal > ORDER_COD_MAX_VND` (`5_000_000`) ở bước này khi `!hasPromotions && !hasShopFreeship`.
6. **Saga Step 1 — Giữ tồn kho**: `Product.ReserveStock(OrderId=checkoutGroupID, Items=allStockItems)` (mang JWT người mua, idempotent theo `checkoutGroupID`). Lỗi → `failGroupBeforePersist`.
7. **Saga Step 2 — Giữ khuyến mãi (khi `hasPromotions`: voucher/xu/flash sale/chương trình giảm giá shop)**:
   - `checkout.go:buildReservePromotionRequest` (truyền đủ `category_id`, `shop_discount_program_item_id`, cấu hình `free_ship_*` của từng shop) → `Promotion.ReservePromotion(OrderId=checkoutGroupID, ...)`.
   - **Bù trừ nếu lỗi**: `checkout.go:compensateReleaseStock` + `failGroupBeforePersist`.
   - `checkout.go:applyDiscountsAndTotals` (trả `error`; nếu lỗi phải bù trừ `compensateReleasePromotion` + `compensateReleaseStock` + `failGroupBeforePersist`):
     - **Nguồn duy nhất từ breakdown**: khi `promoReserved == true`, `breakdown` là nguồn duy nhất cho `F` (Flash Sale), `P_shop` (kèm `applied_shop_program_item_ids`) và `S_shop` (shop freeship).
       - `F`: lệch với `Σ (unit_price - flash_price) * qty` → fail `FLASH_SALE_PRICE_CHANGED`.
       - `P_shop`: chỉ áp giá chương trình và giữ `order_items.shop_program_item_id` cho các item có trong `applied_shop_program_item_ids` của shop; item đã gửi nhưng bị loại (vd. vượt `per_user_limit`) tính theo giá thường và đặt `shop_program_item_id = ""`; ID lạ không nằm trong danh sách đã gửi → fail `SHOP_PROGRAM_ITEM_UNKNOWN`; `P_shop` lệch tổng các item được áp → fail `SHOP_PROGRAM_PRICE_CHANGED`.
       - `S_shop`: chỉ tự tính cục bộ khi `!promoReserved && breakdown == nil`; luôn cắt gọn `S_shop <= Ship` và `S_shop <= merchAfterShopDisc` để `R >= 0`.
     - **Công thức tiền nguyên VND**: `R = G - F - P_shop - V_shop - S_shop >= 0`; `S_free <= Ship - S_shop`; `D = V_plat + S_free + X`; `P = R + Ship - D >= 0` (`P + D == R + Ship`).
     - **Phí danh mục & phí thanh toán**: `C_cat` tính theo đúng `sku.commission_rate_bps` (0..10000, kể cả `0` bps, không còn fallback `ORDER_DEFAULT_COMMISSION_BPS`) trên giá sau giảm sản phẩm (`effectivePrice * qty`), cap `<= R`, snapshot vào `order_items.commission_rate_bps`; `C_pay = P * payment_fee_bps / 10000`, cap `<= R - C_cat` sao cho `C_total = C_cat + C_pay <= R`.
   - **Kiểm tra trần COD sau khuyến mãi** (`checkout.go:336-348`): nếu `COD && grandTotalPayableVND > CODMaxVND` → bù trừ `compensateReleasePromotion` + `compensateReleaseStock` + `failGroupBeforePersist`.
8. **Saga Step 3 — Lưu sub-orders + timeline + outbox trong 1 TX**:
   - Nếu `COD` hoặc `grandTotalPayableVND == 0`: khởi tạo `CONFIRMED` (`payment_status="PENDING"` hoặc `"SUCCEEDED"` nếu 0 VND). Ngược lại (`VIETQR > 0`): `PENDING`, `payment_expires_at = now + ORDER_PAYMENT_EXPIRY_MINUTES` (`15m`); riêng đơn có Flash Sale dùng hạn ngắn `ORDER_FLASH_PAYMENT_EXPIRY_MINUTES` (`5m`), chặn trần bởi `earliestFlashEndsAt`, và không bao giờ để hạn mặc định từ `PaymentService` kéo dài thêm (`RetryPayment` cũng giữ nguyên hạn ban đầu).
   - `checkout.go:buildCheckoutBatch` dựng 1 đơn con/`shop_id` (mã `NM-YYYYMMDD-XXXXXXXX`), lưu tách `commission_vnd = C_cat`, `payment_fee_vnd = C_pay`, `payment_fee_bps`, `shop_program_discount_vnd`, `shop_freeship_discount_vnd`, `order_items` (kèm `category_id`, `commission_rate_bps`, `shop_program_item_id` chỉ của item thực sự áp dụng), `order_timeline_events`, `outbox_events` (`order.created`; nếu `CONFIRMED` ghi thêm `order.confirmed`).
   - `store/postgres.go:PersistCheckoutBatch` chạy dưới `detachedTimeoutContext`, khóa `checkout_groups FOR UPDATE` đòi `status = 'IN_PROGRESS'`, lưu kèm `warnings_json` và `pending_stock_confirm = true` (nếu `CONFIRMED`). Nếu trả lỗi: mở TX tách `InspectCheckoutGroupOrdersLocked` (chờ commit đang dở); thấy đơn → đi tiếp forward; không có đơn → bù trừ (`compensateBeforePersistAndFail`); không đọc được → trả `Unavailable`, không bù trừ, không đánh `FAILED`.
   - **Chặn gửi hàng khi chưa xong payment (`service.go:requireCheckoutPaymentInitialized`)**: khi `checkout_groups.status == 'IN_PROGRESS'`, `SellerConfirmOrder` (`CONFIRMED -> PREPARING`) vẫn cho phép, nhưng `SellerShipOrder` và mọi đường đưa đơn sang `SHIPPING` trở lên (`HandleShipmentUpdated` `FORWARD`, `completeDeliveredOrder`, `RequestReturn`) đều bị chặn với `FailedPrecondition` (`PAYMENT_NOT_INITIALIZED: đơn đang khởi tạo thanh toán, vui lòng thử lại sau ít phút`) trước khi tạo vận đơn.
9. **Saga Step 4 — Tạo thanh toán (luôn gọi, kể cả đơn `0 VND`)**:
   - `checkout.go:buildCreatePaymentRequest` (`IdempotencyKey="checkout:"+checkoutGroupID`, `shop_allocations` mang `subtotal_vnd=R`, `shipping_fee_vnd=Ship`, `platform_discount_vnd=D`, `commission_vnd=C_cat+C_pay`) → `Payment.CreatePayment` gọi bằng `detachedCallerContext` (giữ JWT người mua nhưng không chết theo client cancel).
   - **Lỗi mơ hồ**: probe `Payment.GetPayment(OrderGroupId)` dưới `detachedCompensationContext` + retry. Nếu thấy payment: đồng bộ trạng thái khác `PENDING` qua `reconcileObservedPaymentStatus` (lỗi → trả `Unavailable` ngay, KHÔNG gọi `CompleteCheckoutWithPayment`) rồi hoàn tất tiến. Nếu lỗi probe → trả `Unavailable`, không hủy/nhả. Nếu `NotFound`: đơn `CONFIRMED` (COD / 0 VND) trả `Unavailable` KHÔNG hủy để watchdog phục hồi tiến; đơn `PENDING` (VietQR) đi nhánh hủy.
   - **Nhánh hủy (lỗi xác định hoặc VietQR mơ hồ + `NotFound`)**: dưới `detachedCompensationContext`, gọi `store/postgres.go:CancelCheckoutGroupOrders` (khóa `orders` rồi `checkout_groups FOR UPDATE`, từ chối hủy nếu `grp.Status != 'IN_PROGRESS'` hoặc đơn đã có payment/tracking/paid, trả `HasLiveOrders=true`; lỗi → return ngay không nhả gì). Sau khi hủy gọi `CancelPayment(OrderGroupId)` (`NotFound` bỏ qua), `ReleasePromotion`, `ReleaseStock` (nếu `released=false` thì `RestockOrderItems`); chỉ xóa `pending_cancel_compensation` khi mọi bước thành công.
10. **Xác nhận tồn cho đơn khởi tạo `CONFIRMED`, lưu snapshot & dọn giỏ**:
    - Chạy dưới `detachedCompensationContext` + retry (`completeCheckoutGroupWithRetry`): `store/postgres.go:CompleteCheckoutWithPayment` khóa `orders` rồi `checkout_groups FOR UPDATE`, không hạ cấp trạng thái đã tới (`SUCCEEDED`/`REFUNDED`/`CANCELLED`), bỏ qua không ghi nếu `grp.Status != 'IN_PROGRESS'` (kèm SQL guard `AND status = 'IN_PROGRESS'` và `AND (payment_id = '' OR payment_id = $2)` để không đè `RetryPayment` P2), dựng `response_snapshot_json` từ trạng thái sau ghi. Nếu toàn bộ đơn con đã `CANCELLED` sau commit thì gọi post-commit `cancelPaymentAfterAllCancelled` (ưu tiên gắn cờ retry lên đơn con có `TotalPayableVND > 0`).
    - Nếu `initialStatus == CONFIRMED` (COD hoặc 0 VND): gọi `checkout.go:confirmGroupStockAndClear` (`Product.ConfirmStock` rồi xóa `pending_stock_confirm`; nếu lỗi tạm thời, watchdog `ScanPendingStockConfirms` thử lại).
    - **Saga Step 5**: best-effort `Cart.ClearItems(buyerID, skuIDs)` dưới `detachedCallerContext` → `service.go:notifyOutbox`.

## 3. Bù trừ, Service Token & Allowlist gRPC

- `service.go:detachedCompensationContext(parent, timeout)`: bọc `context.WithoutCancel(parent)` + `clients.WithInternalAdminContext` + timeout `ORDER_GRPC_TIMEOUT` (`10s`), bảo đảm lời gọi bù trừ vẫn chạy xong kể cả khi client ngắt request.
- `services/order/internal/clients/clients.go:WithInternalAdminContext`: xóa raw JWT người mua và gắn claim `Service: "order-service"`, `Role: "admin"`.
- `clients.go:timeoutAndAuthClientInterceptor`: khi `claims.Service != ""` sẽ gọi `svc.SignServiceToken("order-service")` (ký bằng `SERVICE_JWT_SECRET`, TTL `1m` ở `pkg/common/auth/auth.go:SignServiceToken`); ngược lại chuyển tiếp JWT người mua.
- `clients.go:RetryIdempotent`: retry tối đa `3` lần, backoff `50ms` nhân đôi cho `Unavailable`, `DeadlineExceeded`, `ResourceExhausted`. Dùng trong các luồng bù trừ/xác nhận tồn (`compensateReleaseStock`, `compensateReleasePromotion`, `confirmGroupStockAndClear`, `compensateCancelledOrder`, `compensateReturnedOrder`, `restockOrderItemsWithConfirmErr`, `HandlePaymentResult`).
- **Hủy đơn sau checkout** (`lifecycle.go:CancelOrder` → `cancelOrderInternal` → `compensateCancelledOrder`):
  - Nếu đơn đã có `tracking_code` (hoặc `pending_shipment_cancel`), gọi đồng bộ `Shipping.CancelShipment(FORWARD)` dưới service token trước khi chuyển trạng thái (`lifecycle.go:281-289,338-358`); hãng đã lấy hàng (`FailedPrecondition` / `409`) thì giữ nguyên đơn.
  - Nếu đơn đang `PENDING`: `store/postgres.go:TransitionOrderStatus` (`CancelGroupPend=true`) khóa mọi đơn cùng `checkout_group_id` theo thứ tự `shop_id ASC, created_at ASC, id ASC` (tránh AB-BA deadlock với `payment.succeeded`) và hủy cả nhóm `PENDING`, rồi gọi `ReleaseStock`, `ReleasePromotion`, `Payment.CancelPayment`.
  - Nếu đơn đang `CONFIRMED`/`PREPARING`: chỉ hủy đơn đó; đặt bền vững `pending_cancel_compensation=true` (xóa khi mọi bù trừ xong, watchdog `ScanPendingCancelCompensations` thử lại). Không còn sibling active thì gọi `ReleasePromotion` + `ReleaseStock` (nếu đã confirm thì fallback `restockOrderItemsWithConfirmErr`); còn sibling active thì gọi `Promotion.ReleasePromotionShop` + `restockOrderItemsWithConfirmErr` (`Product.ConfirmStock` rồi `Product.RestockOrderItems`). Nếu đã trả VietQR (`wasPaid`) thì gọi `Payment.CreateRefund` (`IdempotencyKey="order-cancel-refund:"+orderID`), nếu chưa trả và không còn sibling thì `Payment.CancelPayment`.
- **Allowlist nhận token service**:
  - Go `pkg/common/auth/auth.go:internalRPCs`: `UserService/{GetAddress,GetProfile,RecordCODRejection,WriteAuditLog,GetShopBankAccountForPayout}`, `ProductService/{ReleaseStock,ConfirmStock,RestockOrderItems,GetCategoryDescendants}`, `PromotionService/{ReleasePromotion,ReleasePromotionShop,CreditCoins}`, `OrderService/MarkPaymentResult`, `ShippingService/{GetShipment,CancelShipment,CreateReturnShipment,GetShopShippingSettings}` (`true`). `ProductService/ReserveStock` và `PromotionService/ReservePromotion` đặt `false` (chỉ nhận JWT người mua).
  - Rust `services/payment/src/auth.rs:SERVICE_METHODS`: `CreatePayment` (chỉ phục hồi tiến từ watchdog `order`: bắt buộc `user_id` không rỗng, `order_group_id` không rỗng, `idempotency_key == "checkout:" + order_group_id`, cấm `supersede_previous = true`), `GetPayment`, `CancelPayment`, `CreateRefund`, `GetFeeConfig` (**không có `ReleaseEscrow`** — `ReleaseEscrow` chỉ nhận JWT `admin`/`super_admin`, giải ngân tự động sau `PAYMENT_SELLER_HOLD_HOURS` do worker nền trong `payment` chạy theo sự kiện `order.completed`).

## 4. Outbox, Consumer NATS & Watchdogs

- **Outbox** (`events/outbox.go:OutboxRelay`, `store/postgres.go:ProcessPendingOutbox`): poll mỗi `250ms` (`ORDER_OUTBOX_POLL_INTERVAL`) hoặc ngay khi `OutboxTrigger()` nhận tín hiệu; khóa batch `50` dòng bằng `queries/orders.sql:LockPendingOutboxEvents` (`FOR UPDATE SKIP LOCKED`), đóng gói `events.Envelope`, đặt header `Nats-Msg-Id = ev.ID` và `traceparent`, publish lên stream `NEXUSMART`.
  - Subject `order` phát ra (`events/types.go`): `order.created`, `order.confirmed`, `order.cancelled`, `order.shipped`, `order.delivered`, `order.returned`, `order.return_updated`, `order.completed`.
- **Consumer** (`events/consumer.go:Consumer.Start`, `ProcessRawMessage`): queue-subscribe `payment.>` (`order-payment-consumer`) và `shipment.>` (`order-shipment-consumer`), `AckWait=30s`, `defaultMaxDeliverAttempts=5`; quá 5 lần hoặc JSON lỗi gọi `sendToDLQ` (ghi bảng `dead_letter_events` + publish `dlq.<subject>`) rồi `Ack`.
  - **Kết quả thanh toán** (`handlers.go:HandlePaymentSucceeded`, `HandlePaymentFailed`, `HandlePaymentExpired` → `handlers.go:HandlePaymentResult`; cộng thêm RPC nội bộ `lifecycle.go:MarkPaymentResult`):
    1. Kiểm `IsEventProcessed(event_id)` và bỏ qua `payment_id` đã bị `superseded`.
    2. Nếu nhóm còn đơn `PENDING`, chạy gRPC downstream **trước** khi commit `processed_events` để lỗi tạm thời kích hoạt NATS redelivery: `SUCCEEDED` → `Product.ConfirmStock`; `FAILED|EXPIRED` → `Product.ReleaseStock` + `Promotion.ReleasePromotion` (bỏ qua `NotFound`).
    3. `store/postgres.go:TransitionOrdersPaymentResult` chèn `processed_events`, chuyển đơn `PENDING → CONFIRMED|CANCELLED`, ghi timeline + outbox (`order.confirmed` / `order.cancelled`) trong 1 TX.
  - **Vận chuyển & hoàn tiền**: `handlers.go:HandlePaymentRefunded` → `store/postgres.go:RecordPaymentRefunded`; `handlers.go:HandleShipmentUpdated` xử lý cả chiều `FORWARD` (`delivering|delivered|failed|returning|returned`; khi `returned` đặt `pending_return_compensation` và chạy `compensateReturnedOrder`: `restockOrderItemsWithConfirmErr`, `ReleasePromotionShop`, `User.RecordCODRejection` cho COD, `Payment.CreateRefund` với `IdempotencyKey="order-return-refund:"+orderID` nếu đã trả VietQR) lẫn chiều `RETURN` (cập nhật `return_requests`: `AWAITING_SHIPMENT -> IN_TRANSIT -> RECEIVED` hoặc `ESCALATED` khi thất bại kết thúc).
- **Watchdogs** (`handlers.go:RunExpiryWatchdog`, tick `10s`, timeout `15s`, chạy 13 sweep theo batch `ORDER BY random()` + khoá từng dòng `FOR UPDATE` trong TX chuyển trạng thái; chỉ outbox relay dùng `FOR UPDATE SKIP LOCKED`):
  - **Payment Expiry (`ScanExpiredPendingOrders` / `processExpiredGroup`, `queries/orders.sql:FindExpiredPendingOrders`)**: trước khi hủy (UC-PAY06), luôn gọi `Payment.GetPayment`:
    - Nếu Payment đã `SUCCEEDED` → xác nhận đơn thay vì hủy.
    - Nếu Payment đã `REFUNDED` → hủy đơn và giữ `payment_status="REFUNDED"` (`PaymentStatusOverride`).
    - Nếu gọi Payment lỗi (khác `NotFound`) → giữ nguyên để tick sau thử lại.
    - Nếu Payment vẫn `PENDING` → gọi `Payment.CancelPayment` (nếu `AlreadyExists`/`FailedPrecondition` thì `GetPayment` lại để rẽ nhánh `SUCCEEDED`/`REFUNDED`; lỗi tạm thời thì trả lỗi giữ nguyên), rồi `HandlePaymentResult(..., EXPIRED)`.
  - **Stale Checkout Cleanup (`ScanStaleCheckoutGroups` / `cleanupStaleCheckoutGroup`)**: nhận quyền trước, nhả sau (2 câu lệnh trong 1 TX `READ COMMITTED`: `GetCheckoutGroupByIDForUpdate` → câu thứ hai `CheckoutGroupHasOrders` kiểm snapshot mới không có đơn → `ClaimCheckoutGroupForCleanup` đặt `status='FAILED', needs_cleanup=TRUE` rồi commit; không thỏa thì không nhả gì). Sau đó `ReleasePromotion` + `ReleaseStock` rồi `ClearCheckoutGroupNeedsCleanup`. `FindStaleInProgressCheckoutGroups` quét cả nhóm `status = 'FAILED' AND needs_cleanup = TRUE` (chưa có đơn) để làm tiếp. Nhánh N9 trong `acquireCheckoutGroup` gọi chung hàm này.
  - **Incomplete Checkout Recovery (`ScanIncompleteCheckoutGroups` / `reconcileIncompleteCheckoutGroup`)**: quét nhóm `IN_PROGRESS` đã có đơn quá hạn; hỏi `GetPayment(OrderGroupId)` trước để hoàn tất tiến. Nếu `NotFound`: dữ liệu cũ có đơn `DELIVERED`/`COMPLETED`/`RETURN_REQUESTED`/`RETURNED` → KHÔNG gọi `CreatePayment`, log Error xử lý tay, không đóng nhóm; toàn `CANCELLED` → `FailCheckoutGroup` + xóa `pending_stock_confirm`; có đơn sống `CONFIRMED`/`PREPARING`/`SHIPPING` → phục hồi tiến bằng service token `CreatePayment("checkout:"+groupID)` chỉ gồm đơn sống (loại `CANCELLED`) và tổng sống; chỉ toàn `PENDING` chưa trả → hủy và bù trừ.
  - **Các sweep còn lại (`handlers.go`)**: `ScanAutoCancelUnconfirmedOrders` (`48h`), `ScanAutoCompleteDeliveredOrders` (`7d`), `ScanReturnDeadlines`, `ScanReturnPendingShipments`, `ScanRefundingReturns`, `ScanPendingOrphanShipmentCancels`, `ScanStalePendingShipmentCancels`, `ScanPendingStockConfirms`, `ScanPendingCancelCompensations`, `ScanPendingReturnCompensations`.

## 6. Optimistic Locking tồn kho SKU (`services/product`)

Schema `services/product/migrations/000001_init.sql`: `skus(stock, reserved_stock, version)` với `CHECK (reserved_stock <= stock)`; `stock_reservations(order_id, sku_id UNIQUE, status IN ('RESERVED','CONFIRMED','RELEASED'))`; `stock_history`.

Cơ chế (`services/product/internal/server/server.go`, `queries/product.sql`, `store/pg_store.go`):
- Sort SKU tăng dần (`normalizeAndSortReservationItems`) tránh deadlock; vòng lặp retry tối đa `maxOptimisticRetries = 8` (`retryBaseDelay = 5ms * attempt`) khi đụng `ErrVersionConflict` hoặc `ErrDuplicateReservation`, vượt trần trả `Aborted` (`STOCK_VERSION_CONFLICT`).
- `Server.ReserveStock`: idempotent theo `order_id` (`AlreadyReserved=true` nếu đã giữ/confirm; lỗi nếu đã `RELEASED`) → `ReserveSKUOptimistic` (`SET reserved_stock = reserved_stock + $1, version = version + 1 WHERE id = $2 AND version = $3 AND (stock - reserved_stock) >= $1`) + `CreateStockReservation` + `InsertStockHistory("RESERVE")`.
- `Server.ReleaseStock`: khóa `ListReservationsByOrderIDForUpdate` → chuyển `RESERVED → RELEASED` (`TransitionStockReservation`) → `ReleaseSKUOptimistic` (trừ `reserved_stock`, tăng `version` theo `WHERE version = $3`) + `InsertStockHistory("RELEASE")`.
- `Server.ConfirmStock`: khóa `ListReservationsByOrderIDForUpdate` → chuyển `RESERVED → CONFIRMED` → `ConfirmSKUOptimistic` (trừ cả `stock` và `reserved_stock`, tăng `version`, chuyển SKU `OUT_OF_STOCK` nếu `stock=0`) + `syncProductStockStatus` + `InsertStockHistory("CONFIRM")`.
- `Server.RestockOrderItems` (service token hoặc admin): cộng tồn nguyên tử idempotent theo `(order_id, sku_id)` qua `stock_history` khi hủy đơn con đã confirm hoặc đơn trả hàng.
- `Server.UpdateStock` (seller chỉnh tồn): `UpdateSKUStockOptimistic` (`WHERE id = $2 AND version = $3 AND $1 >= reserved_stock`), không tự retry để caller tải lại version mới.
